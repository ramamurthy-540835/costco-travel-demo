<objective>
## Goal
Add authenticated regression specs for cancellation/refund (UC3), plus dedicated concurrency-race guards for both the cancellation claim-then-update fix (04-08) and the modification optimistic-lock fix (04-13) — grouped together since both are "two simultaneous requests" tests.

## Purpose
Per the flow inventory, cancellation has a real previously-fixed bug worth regression-locking: the atomic claim-then-update pattern must target the already-`cancelled` document, not the stale in-memory object, or a concurrent-double-cancel would silently revert status. This is exactly the class of bug (a race condition) that manual checkpoint testing structurally cannot catch — it needs two requests fired near-simultaneously, which only an automated spec can reliably reproduce.

## Output
`tests/e2e/regression/cancel.spec.ts` (refund preview/confirm) and `tests/e2e/regression/concurrency.spec.ts` (double-cancel race, concurrent-modify race).
</objective>

```gherkin
Given a reserved booking
When two cancellation requests are fired against it at nearly the same time
```

```gherkin
Given a reserved booking
When two modification requests targeting different inventory (or the same field) are fired at nearly the same time

```

<task type="auto">
  <name>Task 2: Concurrency race-guard specs (double-cancel, concurrent-modify)</name>
  <files>tests/e2e/regression/concurrency.spec.ts</files>
  <action>
    These specs bypass the UI and hit the API routes directly — use Playwright's `page.request` (or `request.newContext({ storageState })`), which automatically shares the browsing context's cookies and works cleanly with Clerk's cookie-based session read. Do not use a raw `fetch`: it has no automatic cookie handling and would require manually parsing `tests/e2e/.auth/user.json` and reattaching cookies, which is error-prone (multiple cookies, domain/path scoping, Clerk session-refresh cookies) and unnecessary here. Bypassing the UI is a deliberate exception — reproducing a true race through UI clicks is unreliable — the goal is to prove the server-side atomicity guard, not the UI's double-click prevention.

    Spec 1 (double-cancel): create a reserved booking. Fire two `POST /api/bookings/[id]/cancel` requests concurrently (`Promise.all`). Assert exactly one response is 200 and the other is 400 ("Only reserved bookings can be cancelled" — confirmed in `cancel/route.ts`; do not assume 409 by analogy with modify's race guard, cancel's is a different status code). Re-fetch the booking from Mongo and assert `status === 'cancelled'` (never `'reserved'` — this is the exact regression 04-08's fix targets) and that only one refund was recorded.

    Spec 2 (concurrent-modify): create a reserved booking. Fire two `POST /api/bookings/[id]/modify` requests concurrently **targeting different inventory** (not just different dates). This is required, not optional: the route's optimistic-lock filter is `{ _id, status: 'reserved', inventoryId: booking.inventoryId, 'pricingSnapshot.totalPrice': booking.pricingSnapshot.totalPrice }` — it does not check `from`/`to`, so two requests that only change dates but land on the same `nights` count (hence identical `totalPrice`) and don't change `inventoryId` would both satisfy the CAS precondition and could both succeed, producing a flaky false pass instead of the intended 409. Changing to different target inventory guarantees the second write's CAS precondition fails. Assert exactly one 200 and one 409. Re-fetch from Mongo and assert `modificationHistory` has exactly one new entry, not two, and the booking's current fields match the one request that actually won — not a merge of both.

    Avoid: assuming which request wins the race — assert on the invariant (exactly one success, final state internally consistent), not on which specific request succeeded, since race outcomes aren't deterministic.
  </action>
  <verify>Both specs pass reliably across at least 3 consecutive local runs (races can be flaky — run a few times to confirm the guard, not just the happy ordering)</verify>
