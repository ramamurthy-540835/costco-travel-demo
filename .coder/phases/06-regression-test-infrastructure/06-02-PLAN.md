<objective>
## Goal
Add authenticated regression specs for booking creation (checkout) — the happy path, the server-side tampered-Stripe-amount rejection (a previously-fixed integrity check, worth locking against regression), and one narrow real-Stripe-Elements smoke test.

## Purpose
Checkout/UC1 is the flow every other regression spec (modify, cancel, add-ons) depends on for its starting booking. Per ROADMAP.md Phase 6 scope, this closes the gap where the rate-integrity check in `app/api/bookings/route.ts` (recompute server-side, compare to Stripe's charged amount, reject on mismatch) has only ever been verified by code review, never a live tampered request.

## Output
- `tests/e2e/regression/checkout.spec.ts`: happy-path booking creation (mocked Stripe network layer) + tampered-amount rejection spec.
- `tests/e2e/regression/payment-smoke.spec.ts`: one `@payment-smoke`-tagged test driving the real Stripe Elements iframe with test card `4242 4242 4242 4242`.
</objective>

```gherkin
Given an authenticated test user at the checkout step

```

    Spec 2 (mismatched-charge rejection, regression-named e.g. `'rejects a PaymentIntent charged below the negotiated rate (regression: rate-integrity)'`): read `app/api/bookings/route.ts` first — confirm there is **no client-supplied price field at all** in the POST body (`{ inventoryId, vendorId, from, to, paymentIntentId, addonIds? }`); the server never trusts a client total. The actual check retrieves the PaymentIntent from Stripe via `stripeAPI.paymentIntents.retrieve(paymentIntentId)` and compares its `amount` (cents) to a fully server-recomputed `expectedAmountCents = dailyRate * nights + addonTotal`. So the only way to genuinely exercise this check is to make the Stripe mock report a PaymentIntent whose `amount` is lower than that expected total — extend `mockStripePayment` (or add a sibling helper in `stripe-mock.ts`) so its intercepted `paymentIntents.retrieve`-equivalent network response (via `page.route` on whatever endpoint/flow surfaces the confirmed PaymentIntent to the client, and ultimately what the server retrieves) returns `status: 'succeeded'` with a reduced `amount`. Drive checkout through to the point where `checkout-form.tsx` calls `POST /api/bookings` with that PaymentIntent's id (this requires the client-side `stripe.confirmPayment` mock to resolve successfully first, same sequencing as the happy path — don't intercept `/api/bookings` before checkout reaches the payment step). Assert the response status is 400 with the real error message ("Charged amount does not match the negotiated rate") and that no new Booking exists for `testMember` afterward (query Mongo directly via the `mongoClient` fixture).

    Avoid: inventing a `total`/`amount` field on the `/api/bookings` request body — no such field exists; the integrity check is entirely server-side against Stripe's own recorded charge, not any client-supplied number.
