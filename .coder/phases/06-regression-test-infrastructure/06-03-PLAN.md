<acceptance_criteria>

## AC-1: Dates-only increase triggers a delta payment and updates pricingSnapshot
```gherkin
Given a reserved booking created via the checkout flow (mocked Stripe)
When the test modifies its dates to a longer/more expensive range and confirms the mocked delta payment
Then the booking's pricingSnapshot.totalPrice increases by the correct delta and modificationHistory records the change
```

## AC-2: Dates-only decrease triggers an automatic refund
```gherkin
Given a reserved booking
When the test modifies its dates to a shorter/cheaper range
Then a refund is issued for the difference (assert via the app's rendered confirmation, not a live Stripe refund lookup) and modificationHistory records refundAmountCents
```

## AC-3: Cross-vendor modification succeeds when the candidate is available, and rejects when it is not
```gherkin
Given a reserved booking and a known-available alternate-vendor candidate
When the test selects it and confirms
Then the booking's inventoryId/vendorId update with a correctly re-derived rate and perks, verified via a direct Mongo read (the app's post-confirmation UI shows only a generic success message, not the new rate/perks)

Given a reserved booking and a candidate the test has made unavailable (e.g. by seeding a conflicting reservation in the target window)
When the test attempts to modify to that candidate
Then the API responds 409 and the original booking is unchanged
```

## AC-4: Modification cutoff rejects a change attempted too close to the rental start
```gherkin
Given a reserved booking whose rental start is within the vendor's modification_cutoff_hours window
When the test attempts any location/vehicle-type change
Then the API responds 400 and the booking is unchanged
```
