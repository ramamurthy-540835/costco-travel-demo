<objective>
## Goal
Port Stripe's PaymentIntent flow from BookCars into a Next.js API route, and port `bookcars-types`' Booking/User/Location/Car shapes into a shared `lib/types/rental.ts`, reshaping `Car` into vendor-owned `Inventory` and adding the `Vendor` entity BookCars never needed.

## Purpose
Closes the remaining Phase 3 port-list items (scoped down per user decision 2026-08-28: PayPal excluded, `mailHelper` deferred to Phase 4 — no consumer exists yet). This is the payment/types plumbing Phase 4's booking UI (04-01) will build against, alongside the 04-00 design prototype.

## Output
- `lib/payment/stripe.ts`: Stripe client singleton (ported from `backend/src/payment/stripe.ts`)
- `app/api/payments/intent/route.ts`: POST endpoint creating a Stripe PaymentIntent (ported from `stripeController.ts`'s `createPaymentIntent` logic)
- `lib/types/rental.ts`: shared TS types ported from `bookcars-types`' `index.ts` — `Booking`, `Member` (renamed from BookCars' `User`), `Location`, `Inventory` (reshaped from BookCars' `Car`), `Vendor` (new), `PaymentResult`, `CreatePaymentPayload`
- `lib/models/Vendor.ts`: new Mongoose model (BookCars has no vendor abstraction — this platform brokers across multiple vendors)
- `.env.local.example`: `STRIPE_SECRET_KEY` placeholder added
</objective>

  <name>Task 1: Port Stripe PaymentIntent flow</name>
  <files>lib/payment/stripe.ts, app/api/payments/intent/route.ts, package.json, .env.local.example</files>
  <action>
    Add `stripe` (`^20.4.1`, matching BookCars' pinned major) to `package.json` dependencies.
    Create `lib/payment/stripe.ts` porting `backend/src/payment/stripe.ts` verbatim in spirit: a singleton `Stripe` client (`new Stripe(process.env.STRIPE_SECRET_KEY!)`), read lazily inside a getter function (not at module scope) so a missing env var doesn't break `next build` — same pattern `lib/mongodb.ts` and `lib/graph/client.ts` already use in this repo.
    Create `app/api/payments/intent/route.ts` porting the `createPaymentIntent` handler logic from `stripeController.ts`:
    - POST body: `{ amount: number, currency: string, receiptEmail: string, description?: string, customerName?: string }`.
    - Validate `amount` and `currency` are present; return 400 with a JSON error body if not, without calling Stripe.
    - Look up or create a `Stripe.Customer` by `receiptEmail` (list then create, matching BookCars' pattern — this list-then-create is what makes repeated calls with the same `receiptEmail` reuse the same `Stripe.Customer` rather than creating duplicates, satisfying AC-5), then call `stripeAPI.paymentIntents.create({ amount: Math.floor(amount * 100), currency: currency.toLowerCase(), receipt_email: receiptEmail, description, customer: customer.id, automatic_payment_methods: { enabled: true, allow_redirects: 'never' } })`.
    - Return 200 with `{ paymentIntentId: intent.id, customerId: customer.id, clientSecret: intent.client_secret }`.
    Add `STRIPE_SECRET_KEY=` placeholder to `.env.local.example` (e.g. `sk_test_...` — literal placeholder text, never a real key).
    Avoid: porting the Checkout Session flow (`stripeAPI.checkout.sessions.*`) — BookCars offers both a hosted-checkout and a direct-PaymentIntent flow; this plan ports only the PaymentIntent flow since that's what a custom Next.js checkout UI (Phase 4) will need, not a Stripe-hosted redirect page.
  </action>
  <verify>With STRIPE_SECRET_KEY set to a real Stripe test key: `curl -s -X POST localhost:3002/api/payments/intent -H 'Content-Type: application/json' -d '{"amount":150,"currency":"usd","receiptEmail":"test@example.com"}' | grep -q clientSecret`; then repeat the same request and confirm the second response's `customerId` matches the first's (AC-5, no duplicate Stripe.Customer created).</verify>
  <done>AC-1, AC-2, and AC-5 satisfied: valid request returns clientSecret, invalid request returns 400 without calling Stripe, repeated calls with the same receiptEmail reuse the same customerId</done>

<task type="auto">
  <name>Task 2: Port bookcars-types + add Vendor entity</name>
  <files>lib/types/rental.ts, lib/models/Vendor.ts</files>
  <action>
    Create `lib/types/rental.ts` porting the following from `packages/bookcars-types/index.ts`, adapted to this platform's vendor-brokerage model (this platform never owns inventory or fulfills rentals — vendors do):
    - `BookingStatus` (string union, not a TS enum): keep BookCars' values but drop `deposit`/`paidInFull`/`paid` distinctions not used by `lib/models/Booking.ts`'s existing `BOOKING_STATUS` — instead, re-export the exact string union already defined in `lib/models/Booking.ts` (`pending | reserved | checked_in | returned | cancelled`) so the type and the Mongoose schema never drift.
    - `Member` (ported from BookCars' `User`, matching `lib/models/Member.ts`'s existing fields — do not reintroduce BookCars' `password`/`accessToken`/`license` fields, Clerk owns identity).
    - `Location` (ported near-verbatim: `_id`, `name`, `latitude`, `longitude`, `country`).
    - `Inventory` (reshaped from BookCars' `Car`): drop `supplier: User` (platform-owned-by-admin concept) and replace with `vendorId: string` (references the new `Vendor` entity, matching `lib/models/Booking.ts`'s existing `inventoryId`/`vendorId` string-ref pattern). Keep pricing fields (`dailyPrice`, `deposit`), `type`, `gearbox`, `seats`, `mileage`, `available`. Drop `[propKey: string]: any` index signature — this repo's ontology has fixed fields, not BookCars' admin-configurable extras.
    - `Vendor` (new — BookCars has no equivalent since it assumes the platform owns the car): `{ _id: string, name: string, minimumRentalDays?: number, priceChangeRate?: number }`, fields ported from BookCars' `User` supplier-role fields (`minimumRentalDays`, `priceChangeRate` already exist there on the admin/supplier user type) but as a standalone entity, not a `User` subtype.
    - `Booking` (ported from BookCars' `Booking`, but only the fields not already covered by `lib/models/Booking.ts`'s Mongoose schema — this type is for API/route payloads, not a duplicate of the Mongoose schema): `{ member: string, inventoryId: string, vendorId: string, from: Date, to: Date, status: BookingStatus }` (named `member`, not `memberId`, to match `lib/models/Booking.ts`'s actual `member: ObjectId` field; typed `string` here since this is the API-payload boundary, not the Mongoose document).
    - `PaymentResult` and `CreatePaymentPayload` (ported verbatim — used by Task 1's route handler and its future callers): `PaymentResult { paymentIntentId: string, customerId: string, clientSecret: string | null }`; `CreatePaymentPayload { amount: number, currency: string, receiptEmail: string, description?: string, customerName?: string }`.
    Create `lib/models/Vendor.ts`: a Mongoose model mirroring `lib/models/Member.ts`'s style (Schema/model/models pattern, `timestamps: true`), fields `name` (required), `minimumRentalDays` (Number, default 1), `priceChangeRate` (Number, default 0).
    Avoid: making `Inventory`/`Vendor` Mongo documents that duplicate the graph's `Vendor`/`Inventory` nodes wholesale — per PROJECT.md, vendor integration stays a separate boundary; `lib/models/Vendor.ts` here is the *platform's own* lightweight vendor record for Mongo-side booking references, not a sync of vendor-owned systems.
  </action>
