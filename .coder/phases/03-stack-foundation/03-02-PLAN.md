<objective>
## Goal
Wire the Next.js app to both operational data stores: MongoDB (booking/member documents) and the Phase 1/2 Postgres+AGE graph (vendor/vehicle-class/negotiated-term reference data) — the second and final vertical slice of Phase 3's Stack Foundation.

## Purpose
Phase 4's booking UI needs somewhere to write bookings (Mongo) and somewhere to read negotiated rates/perks/vehicle classes (the graph). This plan stands up both connections and a first typed query surface, closing the deferred "query-layer contract" noted since Phase 1.

## Output
- A local Mongo instance (docker-compose, mirroring `graph/docker-compose.yml`'s pattern) reachable via `lib/mongodb.ts`
- Mongoose models: `Member`, `Booking`, `AdditionalDriver` (ported from BookCars with vendor-owned-inventory adaptation)
- `lib/graph/client.ts` + `lib/graph/queries.ts`: a typed TS wrapper over the existing Postgres+AGE `rental_graph`, exposing a first set of read queries (vehicle classes, a vendor's negotiated terms, perks for a term)
- `app/api/health/route.ts`: confirms both connections are live in one request
</objective>

<task type="auto">
  <name>Task 3: Graph query layer (TS client over Postgres+AGE)</name>
  <files>lib/graph/client.ts, lib/graph/queries.ts, app/api/health/route.ts, .env.local.example</files>
  <action>
    Add `pg` to `package.json` dependencies (no existing TS AGE client to port — agentic-commerce's graph access is Python-only via `agent-service/`; this is new).
    Create `lib/graph/client.ts`: a `pg.Pool` singleton (cached on `global`, same hot-reload-safe pattern as `lib/mongodb.ts`) reading `GRAPH_DATABASE_URL` from env. Since AGE's `LOAD 'age'`/`search_path` setup is session-scoped and a `pg.Pool` reuses/recycles connections, register `pool.on('connect', (client) => client.query('LOAD \'age\'; SET search_path = ag_catalog, "$user", public;'))` so every pooled connection is initialized, not just the first. Add a `runCypher(query: string, params?: Record<string, unknown>)` helper that executes `SELECT * FROM cypher('rental_graph', $$ ... $$, %s::agtype) AS (result agtype)`, passing `JSON.stringify(params)` as the single bound `%s` argument — mirroring the exact param-binding convention used by `resolve_one` in `graph/scripts/verify_graph.py` (a plain JS array does NOT match AGE's binding shape).
    Create `lib/graph/queries.ts` with the first typed query functions (this is the query-layer contract deferred since Phase 1):
    - `getVehicleClasses(): Promise<VehicleClass[]>`
    - `getNegotiatedTermsForVendor(vendorId: string): Promise<NegotiatedTerm[]>`
    - `getPerksForTerm(termId: string): Promise<Perk[]>`
    Port the `agtype` result-parsing logic from `graph/graph_service/agtype.py`'s `parse_agtype` (translate to TS) rather than re-deriving suffix-stripping from scratch — it already handles the `::vertex`/`::edge` suffix and plain-scalar cases correctly.
    Add `GRAPH_DATABASE_URL=` placeholder to `.env.local.example` (e.g. `postgresql://postgres:localdev@localhost:5434/rental` — matches `graph/docker-compose.yml`'s exposed port).
    Create `app/api/health/route.ts`: calls `connectToDatabase()` (Mongo) and `getVehicleClasses()` (graph) via `Promise.allSettled`, mapping each outcome independently to `mongo`/`graph` status fields (a failure in one must not mask or block reporting the other), returns `{ mongo: 'ok'|'error', graph: 'ok'|'error', vehicleClassCount: number }` with the appropriate HTTP status.
  </action>
  <verify>

    2. `curl -s http://localhost:3002/api/health | grep -q '"vehicleClassCount":9'`
  </verify>
