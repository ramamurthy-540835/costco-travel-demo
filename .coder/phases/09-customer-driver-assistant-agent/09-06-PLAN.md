# Phase 9 Plan 06: A2A Vendor-Agent Verification in the Conversational Booking Flow

## Context

The user hit "Inventory or negotiated rate not found" at the final pay-and-book step (root cause: a vendorId case-mismatch, now fixed in `tools.ts`). While diagnosing it, we confirmed a real architectural gap: `create_booking`/`POST /api/bookings` never calls the Vendor Agent — it only queries the graph directly. A2A (`callVendorSkill`) is wired into `get_quote` and `get_vendor_policy`, neither of which the booking flow actually calls, so the A2A layer built in Phase 8 sits unused for the one path (booking) where a real vendor-side check (live per-date-range availability) matters most.

The user's decision: the **conversational** assistant must go through the Vendor Agent (A2A) before booking — that's the whole point of having a vendor boundary in the agentic experience. The **traditional** `/checkout` flow (non-chat, `app/(checkout)/checkout/checkout-form.tsx` → direct `POST /api/bookings`) is explicitly allowed to keep bypassing it, per the user ("can be avoided during regular or traditional booking experience"). This plan wires A2A into the chat path only, preserving the existing customer-assistant ↔ vendor-agent boundary (mirrors `mastech-agentic-commerce`'s storefront-agent vs. supplier-agent seam) rather than blurring it by calling vendor logic from inside `app/api/bookings/route.ts` itself.

## Non-goals / boundaries

- **No change to `app/api/bookings/route.ts`, `app/(checkout)/checkout/checkout-form.tsx`, or any other non-chat surface.** Direct/traditional checkout keeps its current graph-only behavior exactly as-is.
- **No change to the Vendor Agent's transport or Agent Card** (`agent-service/vendor-agent/server.ts`, `agent-card.ts`) — `check_availability` already exists as a skill and already does the right thing (`checkAvailability()` in `lib/vendor-integration/policy.ts`, a real Mongo overlap query against `reserved`/`checked_in` bookings). This plan is a new *caller* of that skill, not a new skill.
- **No change to `computeBookingTotal`'s pricing/negotiated-term logic** (just fixed for the case-mismatch bug) — availability is a separate, additive gate before pricing, not a replacement for it.
- Does not touch `propose_modification`/`propose_cancellation` — those already read/write against Mongo booking state directly and are out of scope; only the *new-booking* path (`propose_booking`) gains an A2A gate. (`get_quote`'s existing `apply_modification` A2A call remains unused by the modify flow, unchanged — a separate, already-tracked gap, not this plan's concern.)

## Approach

### 1. `propose_booking` gates on a real A2A availability check before pricing
- **`agent-service/customer-assistant/tools.ts`**, `propose_booking` handler: after `computeBookingTotal` resolves a matching row (so we have the canonical `inventoryId`/`vendorId`) but *before* creating the Stripe PaymentIntent, call:
  ```ts
  const availability = await callVendorSkill<{ available: boolean }>('check_availability', {
    inventoryId: totals.inventoryId,
    from: args.from,
    to: args.to,
  });
  if (isVendorTaskError(availability)) {
    return { error: `Vendor availability check failed: ${availability.message}` };
  }
  if (!availability.available) {
    return { error: `${totals.vendorId} reports this vehicle is not available for ${args.from} to ${args.to} — try different dates or another vendor.` };
  }
  ```
  This reuses the existing `callVendorSkill`/`isVendorTaskError` import already in this file (used today by `get_quote`) — no new client code. The A2A hop happens exactly once per proposal, before any PaymentIntent/pendingProposal is created, so a vendor-side "not available" never lets a member pay for something the vendor agent says it can't fulfill.
- **`create_booking` is unchanged** — it still just replays the pendingProposal's args to `POST /api/bookings`. The availability gate lives entirely at proposal time, matching the existing propose/confirm split (propose = quote+checks, confirm = commit) rather than duplicating the check twice.

### 2. System prompt: no user-visible change needed, but document the boundary
- **`agent-service/customer-assistant/chat-loop.ts`**: no new rule needed for the model itself — `propose_booking`'s error contract already tells it to retry/re-search on any `error` field, and "not available for these dates" reads the same way as the existing inventory-mismatch error. Add one short line to the existing `propose_booking` guidance so the model surfaces a vendor-declined-availability error to the member as a plain sentence (not a retry-forever loop): if `propose_booking` returns a vendor-availability error, tell the member and ask if they'd like different dates or another vendor, rather than silently re-calling `propose_booking` with the same args.

### 3. Vendor Agent must actually be running for the chat flow to work
- No code change, but call out explicitly in the SUMMARY (and verify live): the customer-assistant service now has a **hard runtime dependency** on the Vendor Agent (`VENDOR_AGENT_URL`, default `localhost:4100`) for every new booking proposal, where today it had none. If the Vendor Agent is down, `propose_booking` must fail with a clear "vendor availability check failed" error (already covered by the `isVendorTaskError` branch above) rather than hanging or silently skipping the check — confirm this live by stopping the vendor-agent process and re-testing `propose_booking`.

## Critical Files
- `agent-service/customer-assistant/tools.ts` — `propose_booking` handler gains the A2A `check_availability` gate (imports already present)
- `agent-service/customer-assistant/chat-loop.ts` — one-line prompt addition for surfacing a vendor-declined-availability error as plain text
- Reference only, unmodified: `agent-service/customer-assistant/vendor-agent-client.ts`, `agent-service/vendor-agent/skills.ts` (`check_availability`), `lib/vendor-integration/policy.ts` (`checkAvailability`), `app/api/bookings/route.ts`, `app/(checkout)/checkout/checkout-form.tsx`
