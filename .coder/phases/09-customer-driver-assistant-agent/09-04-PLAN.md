# Phase 9 Plan 04: Slot-Filling Discovery + Compact Cards + Pure-Text Intents

## Context

09-03 shipped card rendering for `search_inventory` and a conversational prompt, but live use surfaced three problems (see screenshot): (1) `VehicleCard` in the chat strip is too large (440px, full-size image/detail layout meant for the standalone `/search` page); (2) the assistant jumps straight to results on a bare "get me a sedan" with no city/dates/drop-off/vendor slot-filling, so results are unscoped and can't compute real per-vehicle pricing (nights is hardcoded to `3` in `VehicleResultStrip`); (3) the "Choose this car" button and the Confirm/Cancel proposal buttons are real UI controls — the user wants **every action (picking a car, confirming a booking, paying) to happen as a normal typed/sent chat message (an "intent"), with no buttons anywhere in the chat panel**, including payment, which must happen inline in the chat via an embedded Stripe `PaymentElement` rather than a navigation to `/checkout`.

This extends Phase 9 (reopen per the `06-06`/`09-03` precedent) rather than starting a new phase, since it's a direct follow-on UX correction to 09-03's own delivery.

## Approach

### 1. Slot-filling before `search_inventory` (prompt-only + one new filter)
- **`agent-service/customer-assistant/chat-loop.ts`** `SYSTEM_PROMPT`: replace the current single paragraph about `vehicleClass` with explicit ordered slot-filling rules: before calling `search_inventory`, the assistant must have (a) pickup city, (b) whether drop-off is the same city or a different one (and which, if different), (c) pickup date and return date, (d) whether the member wants a specific vendor/partner or is open to any. Ask ONE missing slot at a time (reuses the prompt's existing "ask for just that one missing thing" rule). Vehicle class stays optional/whenever mentioned, as today. Once all slots are gathered, call `search_inventory` with all of them.
- **`agent-service/customer-assistant/tools.ts`**: extend `search_inventory`'s tool schema with optional `vendorId`, `pickupDate`, `returnDate`, `dropoffCity` params (all strings). Handler:
  - resolves `vendorId` as-is (no synonym table for vendors; exact `provider` match) and passes it into `searchInventory` as a new filter.
  - passes `pickupDate`/`returnDate`/`dropoffCity` straight through into the returned payload (`{ totalMatches, results, pickupDate, returnDate, dropoffCity }`) purely so the frontend can compute real nights/labels — they are not used for graph filtering (per the existing "live availability stays vendor-side" boundary comment already in this file).
- **`lib/graph/queries.ts`**: add an optional `vendorId` filter to `searchInventory()` (not `findEquivalentInventory`, which is out of scope here), following the exact same inline-pattern-property technique already used for `vehicleClassName`/`locationLabel` in that function (see the comment there explaining why a trailing `WHERE` after an `OPTIONAL MATCH` silently fails).

### 2. Smaller cards, real dates, no button
- **`components/vehicle-card.tsx`**: add an optional `compact?: boolean` prop (default `false`, so the existing `/search` page usage is untouched byte-for-byte). When `compact`:
  - `CardImage` renders shorter (`h-24 w-full` vs `h-40`/`sm:w-48`).
  - Layout stays vertical (no `sm:flex-row`), tighter padding/gaps, smaller heading (`text-sm`/`text-base`), fewer badge rows (drop seats/gearbox icons row or collapse to one compact line — keep price, class, vendor+rating, and the top 1-2 perks only).
  - The `Button`/`Link` ("Choose this car") is **not rendered at all** in compact mode. Replace it with a plain muted text hint: `Say "book the {make} {model}" to reserve this one.` (or similar, using vehicle_make/model or class_name as fallback) — plain text, not a link/button element.
- **`components/assistant-chat.tsx`** `VehicleResultStrip`: shrink item width from `w-[440px]` to `w-[240px]`, pass `compact`, and thread the now-real `pickupDate`/`returnDate` (from the `search_inventory` result payload, read off the stored message's tool result) and computed `nights` into `VehicleCard` instead of the current hardcoded default of 3. Store `pickupDate`/`returnDate`/`dropoffCity` alongside `searchResults` on `ChatMessage` (extend the interface) when captured from the `tool_result` event.

### 3. Proposal confirm/cancel becomes pure text, no buttons
- **`components/assistant-chat.tsx`**: delete the `Confirm`/`Cancel` `<Button>`s and the raw `JSON.stringify(m.proposal.result, null, 2)` dump from the proposal block. Replace with a plain-text rendering of the human-relevant preview fields (e.g. total price / dates / cancellation refund amount — whatever's present on `m.proposal.result`) and no controls. Remove `handleConfirm`/`handleCancel` and `proposalConfirmTool` (dead code once buttons are gone).
- **`chat-loop.ts` `SYSTEM_PROMPT`**: add a rule that after any `propose_*` call, the assistant must ask the member in plain text to confirm ("yes"/"no") before ever calling the matching confirm tool (`create_booking`/`modify_booking`/`cancel_booking`) — this is the *replacement* mechanism for the removed Confirm button; the two-step propose/confirm tool contract server-side is unchanged.
- This removes the UI's structural guarantee (AC-3 from 09-02) that a proposal can only be confirmed by an explicit click; the guarantee moves fully to the system prompt (a real, documented trade-off — call this out in the SUMMARY, do not silently drop it).

### 4. Inline Stripe payment in chat (replaces `/checkout` navigation for the assistant flow)
- New **`components/assistant-payment.tsx`**: extract the `Elements`/`PaymentElement`/`confirmPayment` pattern out of `app/(checkout)/checkout/checkout-form.tsx` (lines 228-236, 243-315) into a small standalone component taking `{ clientSecret, paymentIntentId, inventoryId, vendorId, from, to, onDone }`. Reuses `loadStripe(NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY)`, `Elements`, `PaymentElement`, `stripe.confirmPayment({ elements, redirect: 'if_required' })`, then POSTs directly to `/api/bookings` (same direct call `checkout-form.tsx`'s `PaymentStep` already makes — not through the assistant's `create_booking` tool, since that tool requires a pendingProposal match keyed only by `paymentIntentId`, which still works fine either way, but calling `/api/bookings` directly mirrors the existing working path exactly and avoids a second server round-trip through the assistant). `/checkout` page itself is untouched.
- **`components/assistant-chat.tsx`**: when a message's `proposal.toolName === 'propose_booking'`, render `<AssistantPayment>` instead of the (now-removed) Confirm/Cancel block, using `clientSecret`/`paymentIntentId` off `m.proposal.result`. On its `onDone(bookingId)` callback: clear the proposal and call `sendTurn(...)` with a synthetic user-style text turn like `"Payment completed, booking ${bookingId} confirmed."` so the assistant's next reply (and conversation history) naturally acknowledges it — no route redirect, everything stays in the chat panel.
- `propose_modification`/`propose_cancellation` have no payment step — those keep the new plain-text-confirm flow from section 3 unchanged.

### 5. pgvector-backed embedding fallback for discovery
09-03 evaluated and deferred this; the user has now asked to bring it in. Scope it as a **fallback broadening step**, not a replacement for the structured graph+synonym filter (that stays the primary path from section 1) — mirrors agentic-commerce's tiered merge-and-rank.

Current state, confirmed by exploration: the graph Postgres image is `apache/age:release_PG16_1.6.0` (`graph/docker-compose.yml`, schema in `graph/init/01-init-graph.sql`) — **pgvector is not installed**; Azure OpenAI is only configured for chat completions (`agent-service/customer-assistant/env.ts`: `AZURE_OPENAI_ENDPOINT/API_KEY/DEPLOYMENT_NAME`) — **no embeddings deployment exists**; and inventory/perk data (`data/reference/mock-data/rental_inventory.json`, `data/synthetic/perks.json`) has only short structured fields, no free-text description to embed directly.

- **Embedding model: `text-embedding-3-small` (1536 dims)** — matches the model mastech-agentic-commerce already uses for its own pgvector product search (`agent-service/agent_service/storefront/tools/product_search_tool.py`, `agent-service/scripts/backfill_embeddings.py` there), so `vehicle_class_embeddings.embedding` stays `vector(1536)` with no schema change. `AZURE_OPENAI_EMBEDDING_DEPLOYMENT_NAME` (env.ts) now defaults to `'text-embedding-3-small'` rather than requiring an explicit env var — Azure requires the deployment name to match this exactly for the API call to resolve.
- **Resolved — deployment confirmed provisioned:** the Azure OpenAI embeddings deployment `text-embedding-3-small` already exists in the portal; `backfill_embeddings.py` ran successfully against it (12/12 VehicleClass nodes embedded). `embedVehicleClassQuery` in `tools.ts` still catches API failures and degrades to today's zero-result behavior rather than throwing, so a future deployment outage or rename still can't break `search_inventory` — but this is now a safety net, not the expected path.
- **`graph/docker-compose.yml` + new `graph/Dockerfile.pgvector`**: layers `pgvector` on top of the existing `apache/age:release_PG16_1.6.0` base. Building pgvector from source (`git clone` from GitHub inside the Dockerfile) failed in this environment's Docker build sandbox with a TLS "certificate signer not trusted" error on the `git clone` step — confirmed NOT a host-network issue (the host itself has working, unproxied HTTPS to GitHub). Worked around by using the official `pgvector/pgvector:pg16` image as a multi-stage source to copy `vector.so`/`vector.control`/`vector--*.sql` from, instead of compiling from source — simpler and avoids the build sandbox's TLS trust gap entirely. `CREATE EXTENSION IF NOT EXISTS vector;` added to `graph/init/01-init-graph.sql`.
- **Applied to the running container:** the existing `rental_graph_data` volume was already initialized, so Postgres's `/docker-entrypoint-initdb.d/*.sql` auto-run never fires on rebuild/restart (only on a fresh/empty data directory) — the new `CREATE EXTENSION`/table/index SQL was run manually via `docker exec ... psql` against the live container after recreating it with the pgvector-layered image.
- **`graph/init/01-init-graph.sql`**: add a plain (non-AGE) relational table `vehicle_class_embeddings (class_name text primary key, description text, embedding vector(1536))` with an `ivfflat` (or `hnsw`) cosine index — keyed at the `VehicleClass` grain (9 classes), not per-Inventory-row, since class-level semantic descriptions are what a "spacious family car" query needs to match against; per-unit specifics (make/model/rate) stay in the graph as today.
- **New `graph/scripts/backfill_embeddings.py`** (mirrors the existing `backfill_synonyms.py` pattern: Azure OpenAI client, `--labels`-style flag, idempotent upsert): for each `VehicleClass`, synthesize a short natural-language description from its known attributes + synonyms (e.g. "Mid-size sedan — automatic, 5 seats, standard fuel policy; also called a standard sedan or medium car"), embed it via the new Azure embeddings deployment, upsert into `vehicle_class_embeddings`.
- **`lib/graph/queries.ts`**: new `findVehicleClassesBySemanticQuery(queryEmbedding: number[], limit = 3): Promise<string[]>` — plain SQL (`pg` client, not Cypher) cosine-distance ORDER BY against `vehicle_class_embeddings`, returning candidate `class_name`s.
- **`agent-service/customer-assistant/tools.ts`**: in `search_inventory`'s handler, only when `vehicleClass` was supplied but both `resolveSynonym` AND the raw-term fallback produce zero rows from `searchInventory`, embed the member's original free-text `vehicleClass` term (one Azure embeddings call) and retry with `findVehicleClassesBySemanticQuery`'s top candidate class before giving up — this is the exact "something spacious for a family road trip" case 09-03 flagged as embeddings-shaped and the synonym table can't cover.
- This section ships independently gated behind the env var's presence: if `AZURE_OPENAI_EMBEDDING_DEPLOYMENT_NAME` is unset, the fallback is skipped (returns today's zero-result behavior) rather than erroring — so the rest of this plan (sections 1-4) is never blocked on Azure provisioning.
