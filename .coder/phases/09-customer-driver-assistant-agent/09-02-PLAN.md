<objective>
## Goal
Build the member-facing conversational chat widget — a floating launcher + slide-over chat panel mounted globally in the app, streaming from Phase 9-01's `POST /chat` SSE endpoint — mirroring `mastech-agentic-commerce`'s `SearchModal.tsx` shopper-assistant UI pattern (launcher → panel → streamed tokens/tool-call indicators → propose/confirm turn) adapted to this app's existing Dialog/component conventions.

## Purpose
Phase 9's ROADMAP goal is a conversational entry point to booking, not just a backend agent — without a UI this is unreachable by members. Reusing this project's existing Dialog/button primitives (as `booking-modify-dialog.tsx` already does) keeps the widget visually consistent instead of introducing a parallel design system, per PROJECT.md's stack conventions.

## Output
- `components/assistant-launcher.tsx` — floating trigger button, mounted globally
- `components/assistant-chat.tsx` — chat panel: message list, input, SSE client consuming 09-01's `/chat` endpoint, explicit propose/confirm UI turn (renders the diff/summary from a `tool_result` event and requires an explicit "Confirm"/"Cancel" click before sending the confirming chat turn)
- `app/layout.tsx` / `components/header.tsx` — mount point for the launcher
</objective>

<acceptance_criteria>

## AC-1: Launcher is globally reachable, mirrors commerce's mount pattern
```gherkin
Given a signed-in member on any page of the app
When they view the header/layout
Then a chat launcher control is visible and clicking it opens the chat panel — same "always-available assistant" pattern as commerce's Navbar-mounted SearchModal trigger
```

## AC-2: Streamed responses render token-by-token from real SSE events
```gherkin
Given the chat panel is open and Phase 9-01's customer-assistant process is running
When the member sends a message
Then the panel streams the model's `token` SSE events into the message bubble incrementally (not a single blocking response), and renders `tool_call`/`tool_result` events as distinct inline indicators (e.g. "Checking availability...")
```

## AC-3: Mutating actions show an explicit confirm/cancel step before firing
```gherkin
Given the assistant proposes a booking modification/cancellation (a `tool_result` event carrying a `propose_*` diff/summary)
When the panel renders it
Then it shows the diff and two explicit buttons (Confirm / Cancel) — the confirming mutating tool call is only sent after the member clicks Confirm, never automatically after the model's text response alone
```

## AC-4: Auth token forwarded correctly, no member ID ever entered by hand
```gherkin
Given a signed-in member's Clerk session
When the chat panel calls Phase 9-01's `/chat` endpoint
Then it forwards the real Clerk session token (via the same cookie-based mechanism the rest of this app's authenticated fetches use) and never asks the member to type or the code to hardcode a member ID
```
