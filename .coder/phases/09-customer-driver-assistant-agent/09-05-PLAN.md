# Phase 9 Plan 05: Full-Coverage Conversational Actions — Vendor Disambiguation, Add-Ons, Billing/Pickup Summary, Booking History

## Context

09-04 shipped slot-filling discovery, compact cards, pure-text confirm/cancel, and inline Stripe payment. A follow-up coverage review confirmed every other product use case (UC1 discovery/booking, UC2 modification, UC3 cancellation, booking status, vendor cancellation policy) already has a conversational tool — with exactly one gap: **UC6 (Phase 5) standalone add-on/extras management on an already-reserved booking** (`POST /api/bookings/[id]/addons`) has zero coverage in `agent-service/customer-assistant/tools.ts` — it's only reachable via the "Manage extras" dialog UI.

Live review of the UC1 booking flow surfaced three additional, related gaps that must close in the same conversational surface:
1. **Vendor ambiguity**: "book the Toyota Camry" is not sufficient identification — `search_inventory` results can include the same make/model from multiple vendor partners at different rates/perks. The assistant must disambiguate by vendor before proposing, and confirm which vendor's unit it's booking (e.g. "Booking the Toyota Camry from Alamo").
2. **Add-ons must be offered before quoting, not after**: today `propose_booking` has no `addonIds` param at all (09-01's SUMMARY explicitly notes this was deliberately dropped as scope-out — see below). The assistant must ask about extras/add-ons before computing any total, since the total materially changes once add-ons are included.
3. **A distinct billing + pickup summary, separate from payment**: today `ProposalSummary` (09-04) renders one line of text before the payment card. The user wants a clearly separated "final bill" card — itemized total (base + add-ons), and pickup/drop-off location/date/time — that appears before the payment step, not folded into the same one-liner.
4. **Booking history / status must be a first-class conversational intent**: `get_booking_status` already exists (09-01) but the system prompt never calls it out for natural phrasings like "show my previous bookings" or "what's the status of my SUV rental", and its result renders as nothing special today (raw tool-result JSON is never shown to the member directly — it's implicit in the model's own text reply). This plan makes it explicit in the prompt and gives it a real list-card rendering.

This extends Phase 9 (reopen, same `06-06`/`09-03`/`09-04` precedent) rather than a new phase — it is a direct closure of gaps found by using the shipped 09-04 surface, not new product scope.

## Non-goals / boundaries

- **No change to `/api/bookings/[id]/addons`, `/api/bookings`, `/api/payments/intent`, or any Mongo model.** All server-side price/perk/waiver logic and the optimistic-lock CAS stay exactly as-is; this plan only adds a conversational path that calls them, mirroring 09-01's "propose→confirm gate enforced server/session-side, never by the prompt alone" principle.
- **No change to the standalone `/search`, `/bookings`, or "Manage extras" dialog UI** — those pages are untouched; this is purely the chat surface.
- Add-on changes on an **existing reserved booking** (UC6, `.../addons` route) and add-ons chosen **at initial booking time** (`propose_booking`/`create_booking`, `POST /api/bookings`'s own `addonIds` param) are two different code paths today and stay two different tools here — do not conflate them.

## Approach

### 1. Vendor disambiguation at booking time (prompt-only, no new tool)
- **`chat-loop.ts` `SYSTEM_PROMPT`**: add a rule — when the member asks to book by make/model/class alone (no vendor named) and the most recent `search_inventory` result contains more than one match for that make/model, the assistant must ask which vendor before calling `propose_booking` (e.g. "I found the Camry at Alamo ($54/night) and Hertz ($61/night) — which one?"). Once resolved (by the member naming a vendor, or if only one match exists), the assistant states the resolution explicitly in its next message ("Booking the Toyota Camry from Alamo") before continuing to the add-ons question in section 2.
- No tool/schema change — `search_inventory`'s results already include `vendor.provider` per row; this is purely a prompt-following behavior the model already has the data for.

### 2. Add-ons offered before quoting; `propose_booking` accepts them
- **`agent-service/customer-assistant/tools.ts`**:
  - New tool `get_addon_catalog` — no params, wraps `getAddOnsCatalog()` from `lib/graph/queries.ts` (already imported by this app elsewhere), returns `{ addOns: [{ addonId, name, feePerDay }] }`. Used by the model to describe real options instead of guessing names/prices.
  - `propose_booking`'s schema gains optional `addonIds: string[]`.
  - `computeBookingTotal(inventoryId, vendorId, from, to, addonIds)` gains an `addonIds` param and now mirrors `POST /api/bookings`'s own addon-total computation exactly: fetch `getAddOnsCatalog()` + `getWaivedAddOnIds(match.perks.map(p => p.perk_id))` (same two calls that route makes), filter `addonIds` to catalog entries with a numeric `fee_per_day` that are **not** in the waived set, sum `fee_per_day * nights`, add to `dailyRate * nights`. This exactly matches the route's `expectedAmountCents` check so the PaymentIntent created here will always pass that route's amount-match guard later.
  - `propose_booking`'s handler passes the resolved `chargedAddonIds` (not the raw requested list — mirrors the route's own distinction) into the pending-proposal it saves, and returns them plus a per-addon price breakdown and `pickup`/`dropoff` fields (see section 3) in its result object.
  - `create_booking`'s schema/handler already forwards `matched.pendingProposal!.args` verbatim to `POST /api/bookings` — since the pending proposal now includes `addonIds`, no further change is needed there; verify this explicitly during APPLY (existing code path, not a new write).
- **`chat-loop.ts` `SYSTEM_PROMPT`**: add a rule — immediately after vendor is resolved (section 1) and before ever calling `propose_booking`, the assistant must call `get_addon_catalog` and ask the member once, in plain text, whether they want any extras (list 2-3 by name, mention it's optional). Only call `propose_booking` (with or without `addonIds`) after that question has been asked and answered (including an explicit "no").

### 3. Distinct billing + pickup summary card, rendered before payment
- **`tools.ts`** `propose_booking`'s returned object gains structured fields for rendering (not prose): `pickup: { city, date }`, `dropoff: { city, date }` (dropoff city defaults to pickup city — read off the same slots `search_inventory` already threaded through per 09-04 section 1), `lineItems: [{ label, amountCents }]` (`Base rate` + one entry per charged add-on), `totalPrice`. (`clientSecret`/`paymentIntentId`/`inventoryId`/`vendorId`/`from`/`to` stay as 09-04 left them for `AssistantPayment`.)
- **`components/assistant-chat.tsx`**: new `BookingSummaryCard({ result })` component — rendered in place of the current one-line `ProposalSummary` **only** when `proposal.toolName === 'propose_booking'` (other proposal kinds — modify/cancel/addons, see section 4 — keep the existing 09-04 one-line `ProposalSummary`, which is not disturbed). Renders itemized `lineItems`, bold total, and a pickup/drop-off block, styled as a visually distinct card (bordered/shaded) from the `AssistantPayment` card that renders immediately below it once the member confirms in text. `ProposalSummary` itself is refactored minimally: extract its current per-tool-name branching so `propose_booking` routes to `BookingSummaryCard` while `propose_modification`/`propose_cancellation`/`propose_addons` keep today's one-liner.

### 4. UC6 — add-on management on an existing reserved booking
- **`tools.ts`**: three new tools, following 09-01's exact propose→confirm pattern (`savePendingProposal`/`consumePendingProposal`) used by every other mutating tool:
  - `propose_addons({ bookingId, addonIds: string[] })` — looks up the booking (fetch the member's bookings list via `GET /api/bookings` — the same call `get_booking_status`'s handler already makes — and find by id; note the returned Mongo documents key on `_id`, not `bookingId`, so the lookup must match `String(b._id) === args.bookingId`; no new route needed, this plan adds zero new API routes) **only to resolve/validate which booking is meant** — the `.../addons` route itself re-reads `pricingSnapshot` from the DB and recomputes `deltaCents` server-side, so the tool does not need to forward any pricing fields, only `bookingId`. Then calls the existing `.../addons` route with `dryRun: true` to get `{ deltaCents, newTotalPrice, chargedAddonIds }`. If `deltaCents > 0`, also calls `/api/payments/intent` (same call `propose_booking` already makes) for that delta — **`deltaCents` is already in cents, but `/api/payments/intent`'s `amount` field is dollars (it does `Math.floor(amount * 100)` internally, see `app/api/payments/intent/route.ts`); pass `amount: deltaCents / 100`, never the raw `deltaCents`, or the created PaymentIntent will be for 100x the intended charge and later fail the `.../addons` route's `Math.abs(paymentIntent.amount - deltaCents) > 1` check anyway** — and returns `clientSecret`/`paymentIntentId` alongside the preview so the member can pay the increase inline; if `deltaCents <= 0`, no payment step (the route auto-refunds on confirm, same as modify/cancel). Saves a pending proposal keyed the same way `propose_modification` does.
  - `update_addons({ bookingId, addonIds, paymentIntentId? })` — consumes the pending proposal (match on `bookingId`, mirrors `modify_booking`'s exact matching rationale/comment already in the file) and calls the real (`dryRun` omitted) `.../addons` route with the originally-proposed args, never the model's restated ones.
  - Tool descriptions explicitly distinguish this from `propose_booking`'s new `addonIds` param (section 2): this pair is for a booking that **already exists**; `propose_booking`'s `addonIds` is only for add-ons chosen at initial booking time.
- **`chat-loop.ts` `SYSTEM_PROMPT`**: add a rule for "add/remove an extra on my existing booking" intents — resolve the booking (via `get_booking_status` if not already in context), call `get_addon_catalog` if the member hasn't already been shown it this conversation, call `propose_addons` with the full desired add-on set (not a diff — the route replaces the whole list, so the assistant must always pass the complete target set, adding to or removing from what the booking already has), show the plain-text delta preview (extends `ProposalSummary`'s one-liner: "+$14 total — GPS is already waived by your Gold perk" style, reusing `deltaCents`/`chargedAddonIds`), get inline payment only if `deltaCents > 0`, confirm by text, then `update_addons`.
- **`components/assistant-chat.tsx`**: extend the existing 09-04 payment-render condition (`proposal.toolName === 'propose_booking' && clientSecret/paymentIntentId present`) to also cover `proposal.toolName === 'propose_addons'` — same `AssistantPayment` component, same props shape, only rendered when `propose_addons`'s result actually included a `clientSecret` (i.e. `deltaCents > 0`); `AssistantPayment`'s `onDone` callback needs a mode switch (see below) since this path must call `update_addons`-equivalent completion (`POST .../addons`, not `POST /api/bookings`) on success.
  - **`components/assistant-payment.tsx`**: generalize `AssistantPaymentForm`'s post-payment-success branch. Add an optional `mode?: 'create_booking' | 'update_addons'` prop (default `'create_booking'`, so 09-04's booking flow is byte-for-byte unchanged) and an optional `addonsPayload?: { bookingId, addonIds }`. **`AssistantPaymentProps` currently declares `inventoryId`/`vendorId`/`from`/`to` as required strings** (see `components/assistant-payment.tsx`); the `propose_addons` render path has none of these (the addons preview result has no `inventoryId`/`vendorId`/`from`/`to` at all) — this is not just "same props shape": these four fields must become optional (required only when `mode === 'create_booking'`, or restructure via a discriminated union), and the call site in `assistant-chat.tsx`'s `propose_addons` branch must pass `mode="update_addons"` and `addonsPayload={{ bookingId, addonIds: chargedAddonIds }}` without supplying those four. Verify this compiles under `tsc --noEmit` during APPLY. When `mode === 'update_addons'`, POST to `/api/bookings/${bookingId}/addons` with `{ addonIds, paymentIntentId }` instead of `/api/bookings`, and call `onDone` with the booking id already known from `addonsPayload.bookingId` (not read from the response body — that route's response *does* include a `bookingId` field, it's just an echo of the same id already known client-side, so there's nothing new to read).

### 5. Booking history / status as a first-class conversational intent
- **`chat-loop.ts` `SYSTEM_PROMPT`**: add an explicit rule mapping "show my bookings" / "what's the status of my rental" / "do I have any upcoming reservations" phrasings directly to `get_booking_status` (optionally with a `status` filter parsed from the phrasing, e.g. "past bookings" → `status: 'returned'`), rather than relying on the model to infer this only from the tool's schema description.
- **`components/assistant-chat.tsx`**: new `BookingListCard({ bookings })` — compact list rendering (vendor, class/dates, status badge, total) of the array returned by `get_booking_status`'s tool result, mirrors `VehicleResultStrip`'s existing horizontal-scroll-strip pattern at a smaller scale (or a simple vertical list if the count is typically small — decide during APPLY based on real data volume, call out the choice in the SUMMARY). Wired the same way `VehicleResultStrip` is today: captured off the `tool_result` SSE event when `toolName === 'get_booking_status'`, stored on the `ChatMessage`, rendered inline. **This requires a new optional field on the `ChatMessage` interface itself (e.g. `bookings?: BookingRecord[]`, mirroring the existing `searchResults?: InventorySearchResult[]`) plus a new `asBookingList(name, result)` extractor alongside the existing `asSearchResults` — the interface change is not automatic and must be made explicitly during APPLY.**
