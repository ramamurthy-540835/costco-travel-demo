<objective>
Fix the "latest bookings" sort bug (currently sorted by rental pickup date instead of booking-creation date) and extend `get_booking_status` with real filter coverage: exact booking-id lookup, a specific-date filter, a location/city filter, and a hardened vendor filter — all resolved as server-side, indexable query params on `/api/bookings` rather than continuing the client-side workaround pattern already flagged as fragile in `tools.ts`.
</objective>

<context>
`app/api/bookings/route.ts`'s GET handler sorts `.sort({ from: -1 })` — `from` is the rental pickup date, not when the booking was created. "Get me my latest 2 bookings" therefore returns whichever bookings happen to have the latest pickup dates, not the two most recently made. `lib/models/Booking.ts` has `{ timestamps: true }`, so a real `createdAt` field already exists and is unused for sorting.

`agent-service/customer-assistant/tools.ts`'s `get_booking_status` currently supports `status` (passed through as a query param) and `vendorId` (filtered **client-side**, after fetching the member's *entire* booking history — its own code comment calls this a workaround: "vendorId has no backing query param on `/api/bookings`... so it's applied client-side here"). There is no way to look up a specific booking by id, filter by date, or filter by location at all today.

Architectural decision (made now, not deferred): all new filters — `bookingId`, `pickupDate`, `city`, and the existing `vendorId` — become real query params on `app/api/bookings/route.ts`, not client-side filtering in `tools.ts`. Reasons:
1. `vendorId`'s client-side precedent fetches the member's full booking history on every call just to filter it down — wasteful and, per its own comment, was only ever a workaround for the missing query param, not a considered design.
2. `Booking` already has a compound index `{ member: 1, status: 1 }` and a `vendorId` field with its own index (`{ vendorId: 1, from: 1, to: 1 }`) — filtering server-side lets Mongo use them instead of shipping every row over HTTP.
3. `bookingId` is a single-document lookup (`_id` or a unique field) — doing this client-side would mean fetching the entire history just to find one row, which is strictly worse than a direct `Booking.findOne`.
4. The one filter that is NOT a simple Mongo field match — `city` — still resolves server-side inside the route handler (not in `tools.ts`), by first resolving the graph for the set of `inventoryId`s located in that city (`lib/graph/queries.ts`, `Inventory -[:LOCATED_AT]-> Location{city}`), then filtering `Booking.find({ inventoryId: { $in: [...] } })`. This keeps the graph dependency in the Next app (which already talks to the graph elsewhere) rather than pulling graph access into the separate agent-service process.

`pickupDate` (not `createdDate`) is the name chosen for the date filter: in this domain, "book me done on a specific date" almost always means the rental's pickup date (when the car is picked up), not the day the member happened to click Confirm. `from`/`to` already exist as range params for this exact field; `pickupDate` becomes a single-day convenience filter on the same field (`from` within [start of day, next day)).

Booking has no persisted city field — confirmed by reading `lib/models/Booking.ts` in full. The city filter must go through the graph via `inventoryId`, there is no shortcut.

The `createdAt` sort fix also changes ordering for `app/(account)/bookings/page.tsx` ("My Bookings" UI), the only other caller of this route besides `get_booking_status` — it goes from pickup-date-desc to creation-date-desc. This is the intended fix, but it's a second, unplanned consumer of the same route and must be explicitly re-checked, not just assumed fine because it wasn't in scope.
</context>

<acceptance_criteria>
AC-1: GIVEN a member with bookings created at different times but with pickup dates in a different order, WHEN `get_booking_status` is called with `limit: 2`, THEN the two most recently-**created** bookings are returned (not the two with the latest pickup dates).

AC-2: GIVEN a member has a booking with a known id, WHEN `get_booking_status` is called with that `bookingId`, THEN only that single booking is returned (not the member's full history), and a `bookingId` for another member's booking returns no result (ownership still enforced via the existing `member` scoping).

AC-3: GIVEN a member has bookings with different pickup dates, WHEN `get_booking_status` is called with `pickupDate` set to one of those dates, THEN only bookings whose `from` falls on that calendar day are returned.

AC-4: GIVEN a member has bookings for inventory in different cities, WHEN `get_booking_status` is called with a `city`, THEN only bookings whose underlying inventory is located in that city are returned; an unrecognized city returns an empty list, not an error.

AC-5: GIVEN a member has bookings across multiple vendors, WHEN `get_booking_status` is called with `vendorId`, THEN filtering happens server-side (verified by confirming `/api/bookings` receives and applies the `vendorId` query param, not by fetching the full list and filtering after).

AC-6: `npx tsc --noEmit` is clean after all changes.
</acceptance_criteria>

    - Change `.sort({ from: -1 })` to `.sort({ createdAt: -1 })` so "latest" means most-recently-created, matching what `get_booking_status`'s `limit` param actually claims to do.
    - Extend `buildOwnBookingsFilter` (keep it exported and unit-shaped the same way) to accept and apply, in addition to the existing `status`/`from`/`to`:
      - `bookingId`: matches on the document's `_id` (validate it's a valid ObjectId string first; if not, treat as no match rather than throwing).
      - `pickupDate`: a single calendar-day filter on `from` — compute `[startOfDay, startOfNextDay)` in UTC from the given date string and set `from: { $gte: startOfDay, $lt: startOfNextDay }`. When `pickupDate` is present, it **completely replaces** the `from`/`to` range object — do not spread/merge the two into one object (a naive merge produces a nonsensical over-constrained range mixing `$gte`/`$lte`/`$lt` from both). Build the `from` clause as: `pickupDate ? { $gte: startOfDay, $lt: startOfNextDay } : (from || to ? { ...rangeClause } : undefined)` — `pickupDate` wins outright, `from`/`to` are only used when `pickupDate` is absent.
      - `vendorId`: exact match on the existing indexed `vendorId` field.
      - `inventoryIds`: (internal, not a public query param name) when provided as an array, filter `inventoryId: { $in: inventoryIds } }` — this is how the city filter (Task 2) plugs in without `buildOwnBookingsFilter` itself knowing about the graph.
    - Read `bookingId`, `pickupDate`, `vendorId`, and `city` off `searchParams` in the GET handler alongside the existing `status`/`from`/`to`.
    - When `city` is present, resolve it to a list of `inventoryId`s (Task 2's new query) before building the filter; if the city resolves to zero inventory ids, return `[]` immediately (skip the Mongo query entirely — there's nothing to match).
