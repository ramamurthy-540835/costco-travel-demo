<objective>
## Goal
Let a member add or remove extras on an existing `reserved` booking (independent of a date modification), with the same already-included-perk waiver check and server-side price-integrity recompute already enforced at checkout (04-12) and date-modification (04-07) time — closing UC6's "0% of already-included perks re-charged as upsells" for the one add-on entry point that currently doesn't exist: post-booking, dates-unchanged.

## Purpose
04-12 already prevents a perk-covered addon from being double-charged **at checkout**, and 04-07's modify route already re-filters addons against the waived set **when dates/vendor change**. But there is no way today for a member to add a forgotten extra (e.g. a child seat) to an already-reserved booking without going through a full date-modification form. This plan adds that missing entry point using the exact same integrity pattern — never a new, unverified path.

## Output
- `POST /api/bookings/[id]/addons` — recomputes the requested addon set against the booking's *current* perks (unchanged inventory/vendor/dates), waives already-included ones, computes the price delta, and (for an increase) requires a paid Stripe PaymentIntent before applying; for a decrease, auto-refunds the difference via the same pattern 04-08 established for decreasing modifications.
- A "Manage extras" dialog on the confirmation page and My Bookings list, mirroring `BookingModifyDialog`'s shape.
</objective>

<acceptance_criteria>

## AC-1: Already-included addon cannot be added as a paid extra
```gherkin
Given a reserved booking whose vendor's negotiated-term perks waive "child_seat" (via a Perk-[:WAIVES]->AddOn edge)
When the member requests to add "child_seat" through POST /api/bookings/[id]/addons
Then the server charges $0 for it and the response marks it as included, never adding it to the priced total
```

## AC-2: Increasing the addon set requires a matching paid PaymentIntent
```gherkin
Given a reserved booking and a non-waived addon with fee_per_day > 0
When the member requests to add it without dryRun and without a valid succeeded PaymentIntent covering the delta
Then the API returns 400 and the booking's pricingSnapshot is unchanged
```

## AC-3: Decreasing the addon set auto-refunds the difference
```gherkin
Given a reserved booking with a previously-charged, non-waived addon already applied and paid for
When the member removes that addon through the addons endpoint
Then a Stripe refund is issued for the exact per-day fee times the remaining nights, idempotency-keyed, and pricingSnapshot.addonIds/addonTotal are updated to reflect the removal
```

## AC-4: Ownership and status are enforced
```gherkin
Given a booking owned by a different member, or a booking not in "reserved" status
When any member calls POST /api/bookings/[id]/addons
Then the API returns 404 (ownership mismatch, hiding existence) or 400 (wrong status) respectively, and never touches Stripe
```

## AC-5: UI entry point matches existing conventions
```gherkin
Given a reserved booking on the confirmation page or My Bookings list
When the member opens "Manage extras"
Then they see the current perks-covered vs. paid addon state, can toggle non-waived addons, see a live recalculated total, and confirm — using the same dialog/Elements pattern as BookingModifyDialog/BookingCancelDialog
```

  <name>Task 1: POST /api/bookings/[id]/addons — dry-run + apply with integrity recompute</name>
  <files>app/api/bookings/[id]/addons/route.ts</files>
  <action>
    New route, modeled directly on `app/api/bookings/[id]/modify/route.ts`'s structure (auth → fetch booking → ownership check via Member.findOne + string compare, 404 on mismatch → 400 if status !== 'reserved').
    Body: `{ addonIds: string[]; dryRun?: boolean; paymentIntentId?: string }` — `addonIds` is the FULL desired set (not a delta), matching how `pricingSnapshot.addonIds` is already stored.
    - Do NOT call `quoteModification()` — this endpoint never changes inventoryId/vendorId/dates, so re-deriving perks/rate from a fresh graph lookup is both unnecessary and a spurious failure mode (a vendor delisting inventory or changing a negotiated term later would 400 an unrelated addon-only request). Instead read `perkIds` and `dailyRate` straight off `booking.pricingSnapshot` — the immutable-by-design snapshot from booking/modification time (see `Booking.ts`'s comment on why a later graph rate change must not retroactively alter a confirmed booking; the same reasoning applies here).
    - `getAddOnsCatalog()` + `getWaivedAddOnIds(booking.pricingSnapshot.perkIds)`.
    - `chargedAddonIds = addonIds.filter(id => catalog has id && !waived.has(id))` — exactly 04-12's booking-creation filter shape.
    - `nights` from booking.from/to (unchanged).
    - `newAddonTotal = sum(fee_per_day * nights for chargedAddonIds)`; `newTotalPrice = booking.pricingSnapshot.dailyRate * nights + newAddonTotal` (base rate is always read from the snapshot, never from a fresh graph/quote lookup — this endpoint only changes extras).
    - `deltaCents = round(newTotalPrice*100) - round(booking.pricingSnapshot.totalPrice*100)`.
    - `dryRun === true` → return `{ deltaCents, newTotalPrice, chargedAddonIds }`, no Stripe/Mongo writes (unconditional first check, per 04-07's fixed dry-run bug — never fall through to the real path).
    - `deltaCents > 0`: require `paymentIntentId`, retrieve it, require `status === 'succeeded'` and `Math.abs(paymentIntent.amount - deltaCents) <= 1` — else 400, no save. Mirrors modify route's increase branch exactly.
    - `deltaCents < 0`: reuse the exact refund pattern from `modify/route.ts`'s decrease branch — retrieve `booking.paymentIntentId` with `expand: ['latest_charge']`, compute `amountRefunded` off `latest_charge`, `refundAmountCents = min(-deltaCents, paymentIntent.amount - amountRefunded)`, `refunds.create(..., { idempotencyKey: \`addons-refund-${booking._id}-${booking.modificationHistory.length}\` })` if positive. On a thrown Stripe error, return 500 without saving.
    - **Optimistic-lock the write** — this route and `modify/route.ts` can both be triggered concurrently against the same `reserved` booking (two dialogs open, a double-click), and neither route today has a guard against a lost-update race on `pricingSnapshot`. Apply the update via `Booking.findOneAndUpdate({ _id: booking._id, status: 'reserved', 'pricingSnapshot.totalPrice': booking.pricingSnapshot.totalPrice }, { $set: { 'pricingSnapshot.addonIds': chargedAddonIds, 'pricingSnapshot.addonTotal': newAddonTotal, 'pricingSnapshot.totalPrice': newTotalPrice }, $push: { modificationHistory: {...} } }, { new: true })` — never a plain `.save()` on the in-memory object. If the filter matches nothing (another write already changed `totalPrice` since this request read it, or the booking is no longer `reserved`), return 409 with a "this booking changed, please retry" message; a Stripe refund already issued in this request must not be silently lost — log/surface it in the error response so the member isn't double-charged-then-ignored on retry.
    - On success: `modificationHistory` entry reuses the existing subdocument shape (`from`/`to`/`inventoryId`/`vendorId` copied unchanged from the current booking, plus `refundId`/`refundAmountCents` if a refund occurred) so the addon change is auditable the same way a date change is — no code elsewhere assumes a `modificationHistory` entry implies a date/inventory delta (confirmed: only this plan's and 04-07's code read the array, both additively).
    - Response: `{ bookingId, totalPrice: newTotalPrice, deltaCents, chargedAddonIds, refundAmountCents, refundId }`.
    Avoid: introducing a second, divergent addon-filtering implementation — call the same `getAddOnsCatalog`/`getWaivedAddOnIds` helpers 04-11/04-12 already added, don't reimplement the Cypher. Avoid: calling `quoteModification()` (see above — dropped from this task entirely).
  </action>
  <verify>
    `npx tsc --noEmit` clean. Manual dry-run curl against a real reserved booking with a waived addon_id in the request returns `chargedAddonIds` excluding it and `deltaCents` reflecting only non-waived additions.
  </verify>
