<objective>
## Goal
Wire the full discovery→checkout flow end-to-end for the first time: a real landing page linking into `/search`, a working "Choose this car" action on each `VehicleCard`, a real checkout page that takes payment via Stripe (test mode) and creates a real `Booking`, and a booking-confirmation page — closing UC1 (member booking with negotiated rate + perks).

## Purpose
UC1 (booking with negotiated rate + perk display) is the platform's first high-priority use case per PROJECT.md. Every piece before this plan (graph query layer, real search UI, Stripe PaymentIntent endpoint, Booking/Member Mongo models) exists in isolation — nothing lets a member actually go from landing on the site to holding a confirmed reservation. This plan closes that gap.

## Output
- `app/page.tsx` — real landing page with a search entry point into `/search` (replaces the Phase-3 placeholder)
- `components/vehicle-card.tsx` — "Choose this car" navigates to `/checkout` with the selected inventory/vendor
- `app/(checkout)/checkout/page.tsx` — real checkout UI: booking summary + Stripe Elements card form
- `app/api/bookings/route.ts` — POST endpoint: creates/reuses a `Member` from the signed-in Clerk user, confirms the Stripe PaymentIntent succeeded, writes a `Booking` with a frozen `pricingSnapshot`, records a graph reservation edge
- `lib/graph/mutations.ts` — first graph **write** query, `recordReservation()` (deferred since Phase 1)
- `lib/models/member-sync.ts` — `getOrCreateMember(clerkUserId, email, fullName)` helper (the deferred Clerk↔Mongo Member sync, minimal form needed to satisfy `Booking.member`)
- `app/(checkout)/confirmation/[bookingId]/page.tsx` — booking-confirmation screen showing the real, saved booking
</objective>

<acceptance_criteria>

## AC-1: Landing links into a real search, and a search result leads to checkout
```gherkin
Given a visitor at "/"
When they land on the real (non-placeholder) landing page and use its search entry point
Then they arrive at "/search" with their input carried as query params

Given a member viewing search results at "/search"
When they click "Choose this car" on a VehicleCard
Then they arrive at "/checkout" with that result's inventory/vendor identified (e.g. via query params)
```

## AC-2: Checkout creates a real Booking with a frozen pricing snapshot, only when the paid amount matches the negotiated rate
```gherkin
Given a signed-in member on "/checkout" for a specific inventory item
When they submit valid Stripe test-mode card details and the PaymentIntent succeeds
  AND the PaymentIntent's charged amount matches the server-recomputed negotiated total (in cents)
Then a Booking document is created in Mongo with status "reserved", the correct inventoryId/vendorId,
  and a pricingSnapshot matching the negotiated rate/perks shown at checkout — not re-queried from a
  possibly-changed graph state after payment

Given the PaymentIntent succeeded but its charged amount does NOT match the server-recomputed total
  (e.g. a tampered client-side amount)
Then /api/bookings rejects with 400 and no Booking is created
```

## AC-3: Booking confirmation page shows the real, saved booking
```gherkin
Given a Booking was just created by the checkout flow
When the member is redirected to its confirmation page
Then the page displays that Booking's real _id, dates, vehicle class, vendor, and total price
  (read from Mongo, not from client-side state)
```

<task type="auto">
  <name>Task 2: Graph write mutation + Member sync + booking-creation API</name>
  <files>lib/graph/mutations.ts, lib/models/member-sync.ts, app/api/bookings/route.ts, package.json</files>
  <action>
    `lib/graph/mutations.ts` (new file): add `recordReservation(inventoryId: string, memberId: string, negotiatedTermId: string)`.
    Use a parameterized Cypher `MERGE (m:Member {member_id: $memberId}) WITH m MATCH (i:Inventory {rental_id: $inventoryId})
    CREATE (m)-[:RESERVED {negotiated_term_id: $negotiatedTermId}]->(i) RETURN true` — `MERGE`, not `MATCH`+`CREATE`,
    for the Member node: a plain `MATCH` would silently no-op (and never create the edge) the first time a given
    member books, while an unconditional `CREATE` would duplicate the Member node on every subsequent booking by
    the same member. Pass `memberId`/`inventoryId`/`negotiatedTermId` as bound parameters through `runCypher()`
    from `lib/graph/client.ts` — never interpolate these into the Cypher string (this is the project's first
    graph **write**; the existing read queries' parameterization pattern must carry over here with the same
    rigor). Pass `columns: ['ok']` for the single-column `RETURN true`, following 04-04's established pattern
    for AGE's column-arity requirement. Confirm the AGE version in this project's `docker-compose` actually
    supports `MERGE` (Apache AGE's `MERGE` support has historically been partial across versions) — if it does
    not, fall back to an explicit `OPTIONAL MATCH` + conditional `CREATE` guarded by a `WHERE m IS NULL` pattern
    instead, and note the deviation in the SUMMARY.

    `lib/models/member-sync.ts` (new file): `getOrCreateMember(clerkUserId: string, email: string, fullName: string)`
    — queries `Member` (from `lib/models/Member.ts`) by `clerkUserId`; if none exists, creates one. This is the
    minimal form of the Clerk↔Mongo Member sync deferred since Phase 3 (STATE.md Deferred Issues) — a full
    webhook handler is NOT in scope here; this is a lazy find-or-create called only from the booking API route.
    Callers MUST source `email`/`fullName` from Clerk's server-verified session (e.g. `currentUser()` from
    `@clerk/nextjs/server`), never from the client-supplied request body — the request body is not a trusted
    identity source.

    `app/api/bookings/route.ts` (new): `POST` handler. Require `auth()`/`currentUser()` from `@clerk/nextjs/server`
    (401 if no signed-in user). Accept `{ inventoryId, vendorId, from, to, paymentIntentId }` in the body — note
    the client may NOT supply `amount`, `pricingSnapshot`, or identity fields; those are always server-derived
    below. Call `getStripe()` and retrieve the PaymentIntent by id: reject with 400 if `status !== 'succeeded'`.
    Re-fetch the specific inventory's current vendor negotiated term via `searchInventory()`'s already-established
    lowest-rank-term resolution (reuse `lib/graph/queries.ts`, do not duplicate the vendor-term lookup logic) to
    build the `pricingSnapshot` fields (`negotiatedTermId`, `dailyRate`, `currency`, `perkIds`, `totalPrice`
    computed from `from`/`to`). **Required integrity check**: compare `paymentIntent.amount` (cents) against
    `Math.round(totalPrice * 100)` — if they don't match, reject with 400 and create nothing (a tampered
    client-side amount must never result in a Booking, regardless of Stripe's charge having succeeded — this is
    this phase's core rate-integrity guarantee). Only once amount is verified: call
    `getOrCreateMember(clerkUserId, currentUser's email, currentUser's fullName)`, create a `Booking` (status
    `'reserved'`) via the Mongoose model from `lib/mongodb.ts`'s `connectToDatabase()`, then call
    `recordReservation()`. Return `{ bookingId }` on success (201).
  </action>
  <verify>
    npm run build (clean). Write and run a one-off local script (e.g. `scripts/_tmp-verify-mutation.ts`, deleted
    after use, matching 04-04's precedent for temp verify scripts) that calls `recordReservation()` directly
    against a test member/inventory id and confirms it succeeds without a Postgres/AGE syntax or arity error —
    do this BEFORE the checkpoint's full Stripe run, so a broken mutation is caught here, not misdiagnosed as a
    Stripe issue three steps later. Also confirm via a direct cypher read that re-running `recordReservation()`
    for the same member a second time does not create a duplicate Member node (proves `MERGE` semantics, not
    `CREATE`).
  </verify>
  <done>Graph write path and booking-creation API are proven correct in isolation, including rejecting a tampered payment amount, before any live payment is attempted.</done>
</task>
