<objective>
## Goal
Let a member cancel a `reserved` Booking — through a real "Cancel booking" affordance on the confirmation page AND from the new "My Bookings" list page (04-07's Task 4), not just an API and not restricted to one booking's own confirmation URL — with the refund amount computed server-side from the real per-vendor `VendorPolicy` graph node (cancellation window, no-show fee) rather than a hardcoded flat rule, and actually issued via a Stripe refund against the original PaymentIntent.

## Purpose
Closes UC3 (Cancellation & refund reconciliation). PROJECT.md's constraints are explicit that "Vendor cancellation/rate policies vary by contract — the platform must handle per-vendor policy variance, not a single hardcoded rule." `getVendorPolicy()` already exists and is already loaded into the graph (`GOVERNED_BY` edge) but has never been queried by any route until this plan.

This revision folds in the same two changes 04-07 got, by the same user direction:
1. **UI, not API-only.** A "Cancel booking" affordance goes on the real confirmation page (`app/(checkout)/confirmation/[bookingId]/page.tsx`), reusing 04-12's shadcn `Card`/`Button` conventions — a confirm-dialog pattern rather than a form, since cancellation has no inputs to collect, just a policy preview and a confirm action.
2. **The same vendor-integration boundary module 04-07 introduces.** `lib/vendor-integration/policy.ts` (created by 04-07) gains a second export, `quoteCancellation()`, wrapping `getVendorPolicy()` + the window/no-show-fee math behind a stable function signature — exactly the pattern 04-07 establishes for modification rate-requoting. This plan does not duplicate the boundary module or invent a second one; it's the second, and last for this phase, consumer of the same seam.
3. **The same "My Bookings" list page 04-07 introduces.** `app/(account)/bookings/page.tsx` (created by 04-07's Task 4) gains a "Cancel" entry point per `reserved` row, alongside 04-07's "Modify" entry point — symmetric with the boundary-module file-existence handling: if 04-07 hasn't applied yet, this plan creates the page itself (list + filters, Cancel only) rather than waiting on it.

**Fold-in (2026-09-03, during 04-07's live checkpoint):** a decreasing modification (04-07's route) previously left the member's original higher charge in place with no refund — 04-07's UI copy said so explicitly ("not issued automatically; contact support"). Per user decision, this plan now closes that gap instead of leaving it as a permanent disclosed limitation: Task 7 below extends `app/api/bookings/[id]/modify/route.ts`'s real (non-dry-run) apply path so that when `deltaCents < 0`, it issues an automatic Stripe refund of the difference against the booking's original PaymentIntent — reusing the same `refunds.create` + idempotency-key pattern this plan already introduces for full cancellation (Task 4), not a third, divergent refund mechanism. This is why `depends_on` now includes `04-07` (this plan edits its route file) and why the previous "does not depend on 04-07's route/UI functionally" boundary line below no longer holds for this one path.

**Correction from the first adversarial review round (still valid, carried forward):** the actual seeded `VendorPolicy` node (confirmed by reading `data/synthetic/vendor_policies.json` and `lib/graph/queries.ts`'s `VendorPolicy` interface) has field `standard_cancellation_window_hours` (not `cancellation_window_hours`), plus `no_show_fee_applies: boolean` and `refund_processing_days: number` — but no numeric penalty-percentage field, and all 10 seeded vendors currently carry identical values. This plan adds one new real field — `no_show_fee_percent` (0-100, varying deterministically by vendor) — to the seed data before writing the route, so the refund calculation reads genuine per-vendor variance rather than a boolean flag.

<acceptance_criteria>

## AC-1: Cancellation inside the free window refunds in full
```gherkin
Given a `reserved` Booking whose vendor's VendorPolicy has `standard_cancellation_window_hours: 24`, and the current time is more than 24 hours before the booking's `from` date
When the owning member confirms cancellation through the "Cancel booking" dialog on their confirmation page
Then a Stripe refund for 100% of the original PaymentIntent amount is created, the Booking's status becomes `cancelled`, `cancellation.refundPercent` is 100, and the confirmation page (after refresh) reflects the cancelled state
```

## AC-2: Cancellation inside the penalty window issues a partial (or zero) refund per policy
```gherkin
Given the same Booking, but the current time is inside the vendor's cancellation window, and that vendor's seeded `no_show_fee_percent` is, say, 30
When the owning member cancels
Then the refund is 70% of the original PaymentIntent amount — derived from that vendor's real `no_show_fee_percent` via `quoteCancellation()`, not a platform-wide constant — and a different vendor with a different seeded `no_show_fee_percent` produces a different refund for the same-shaped cancellation
```

## AC-3: Only a reserved booking can be cancelled, and only by its owner
```gherkin
Given a Booking that is already `cancelled`, or belongs to a different member
When a cancel request is made against it (directly via the API, bypassing the UI)
Then the API returns 400 (already cancelled/wrong status) or 404 (not owned) respectively, and no Stripe refund call is made
```

## AC-4: A booking with no successful payment cannot produce a refund call
```gherkin
Given a Booking whose `paymentIntentId` does not correspond to a succeeded PaymentIntent
When cancellation is attempted
Then the route returns 400 rather than calling Stripe refunds.create with an invalid/unpaid intent
```

## AC-5: The refund policy calculation lives only in the vendor-integration boundary module
```gherkin
Given the cancel route needs the vendor's cancellation-window/no-show-fee rule
When it needs that data
Then it calls `quoteCancellation()` from `lib/vendor-integration/policy.ts` — it does not call `getVendorPolicy()` or compute the window/fee comparison inline in the route itself
```

## AC-6: The confirmation-page dialog shows the real policy-derived preview before confirming
```gherkin
Given a member opens the "Cancel booking" dialog for a reserved booking
When the dialog renders
Then it shows the refund percentage/amount that `quoteCancellation()` would compute for the current moment (via a dry-run call to the cancel route or an equivalent preview call), not a placeholder or a client-guessed number, before the member confirms. (This preview can, in principle, go stale if the member leaves the dialog open across the vendor's exact cancellation-window boundary before confirming — an accepted, hours-scale edge case, not one this plan guards against; see Boundaries.)
```

## AC-7: My Bookings exposes Cancel per-row, without needing the booking's own confirmation URL
```gherkin
Given a signed-in member viewing `/bookings` with a `reserved` booking in the list
When they open that row's "Cancel" action
Then the same refund preview and confirm flow as the confirmation page's dialog runs (same `BookingCancelDialog` component, not a divergent implementation), and after confirming, the row reflects `cancelled` status without navigating to that booking's confirmation page
```

## AC-8: A decreasing modification automatically refunds the difference
```gherkin
Given a `reserved` Booking with a succeeded PaymentIntent, modified (via 04-07's modify route) to a cheaper date range such that `deltaCents < 0`
When the member confirms the change (not a dry run)
Then a Stripe refund of exactly `-deltaCents` is issued against the original PaymentIntent, the Booking's new `pricingSnapshot` is saved, the corresponding `modificationHistory` entry records `refundId`/`refundAmountCents`, and the UI confirms the refund amount to the member — no manual "contact support" step is required
```

Return `{ bookingId: String(booking._id), refundAmountCents, refundPercent: quote.refundPercent }` with 200.
