<objective>
## Goal
Extend the modification API (`app/api/bookings/[id]/modify/route.ts`) so a member can change a reserved booking's `inventoryId`/`vendorId` (location/vehicle-type), not just dates — with an availability check against concurrent bookings, a correct cross-vendor re-quote, a modification-cutoff gate, and a real optimistic-lock write. This plan is API-only; the location/vehicle-type picker UI is 04-14.

## Purpose
04-07 deliberately left inventory/vendor changes unguarded at the route level (accepted from the request body with no check) even though the UI never exposed them. Per PROJECT.md's constraint that the platform must never let a rate/inventory change silently double-book or misapply a vendor's negotiated terms, this closes that gap using the boundary module (`lib/vendor-integration/policy.ts`) as the seam Phase 6's real Vendor Integration Layer will later replace with an RPC call — per the research in `.coder/research/04-13-modify-location-vehicle-type.md` and `.coder/research/agentic-boundary-for-04-13.md`.

## Output
- `lib/graph/queries.ts`: new `findEquivalentInventory()` — graph read returning inventory *candidates* only (never a substitute for the availability check).
- `lib/vendor-integration/policy.ts`: new `checkAvailability()` (Mongo-backed today, real RPC call in Phase 6) and a modification-cutoff helper reused from `quoteCancellation()`'s existing `VendorPolicy` lookup.
- `app/api/bookings/[id]/modify/route.ts`: accepts a target `inventoryId`/`vendorId` change, sequences availability → cutoff gate → quote → optimistic-lock write.
</objective>

<acceptance_criteria>

## AC-1: Availability check blocks a conflicting target inventory
```gherkin
Given a target inventoryId already has an overlapping `reserved` or `checked_in` booking for an overlapping date range (pending bookings excluded)
When a member submits a modification changing inventoryId to that target
Then the API returns 409 with no database write, and the original booking is unchanged
```

## AC-2: Cross-vendor re-match applies the new vendor's own rate and perks
```gherkin
Given a modification targets an inventoryId belonging to a different vendor than the current booking
When the modification is applied
Then the new pricingSnapshot reflects the target vendor's own NegotiatedTerm/perk set (via quoteModification against the new vendor), not the original vendor's, and getWaivedAddOnIds() is re-run against the new perk set before recomputing any addon total
```

## AC-3: Modification-cutoff gate enforced for location/vehicle-type changes
```gherkin
Given the target vendor's VendorPolicy.modification_cutoff_hours indicates the pick-up is too soon
When a location/vehicle-type change (not a dates-only change) is requested
Then the API returns 400 with a clear error and makes no write
```

## AC-4: Optimistic-lock write closes the lost-update race
```gherkin
Given two concurrent modification requests target the same booking
When both attempt to write their result
Then exactly one succeeds via a findOneAndUpdate CAS matched on { _id, status: 'reserved', inventoryId: <prior value>, 'pricingSnapshot.totalPrice': <prior value> }, and the other receives a 409 reflecting that the booking has already changed, never a silent overwrite — the inventoryId guard specifically closes the case where a concurrent swap to a same-priced alternative would otherwise pass a totalPrice-only check undetected
```

Convert `from`/`to` to `Date` objects once at the top of the handler (`const fromDate = new Date(from); const toDate = new Date(to);`) — `checkAvailability`/`checkModificationCutoff` take `Date`, not the route's ISO-string body fields.     3. Call the existing `quoteModification()` against the **target** `inventoryId`/`vendorId` (not the booking's current values) to get the new rate/perks — this call already fails if `inventoryId`/`vendorId` don't form a real pair, so no separate cross-vendor validation is needed.     4. Re-run `getWaivedAddOnIds()` against the new quote's `perkIds` before recomputing any addon total that carries forward — mirrors 04-07's existing same-vendor addon re-filter logic, just pointed at the new vendor's perk set.
    5. On apply (not dry-run), replace the existing plain `.save()` with a `findOneAndUpdate` CAS: `{ _id: booking._id, status: 'reserved', inventoryId: booking.inventoryId, 'pricingSnapshot.totalPrice': booking.pricingSnapshot.totalPrice }` → set the new `inventoryId`/`vendorId`/`pricingSnapshot`/`modificationHistory` entry, `{ new: true }`. The `inventoryId` guard (not just `totalPrice`) is required — a concurrent swap to a same-priced alternative unit must also be caught as a conflict, not just a price change. On `null` result, return 409 `{ error: 'Booking was modified concurrently, please retry' }` — mirrors `addons/route.ts`'s existing pattern (see `app/api/bookings/[id]/addons/route.ts:139-154`), extended with the extra `inventoryId` guard field. This also closes the CAS gap for the existing dates-only path — apply the same CAS (including the `inventoryId` guard) to that branch too, not just the new inventory/vendor branch.
    Skip Steps 1-2 entirely when `inventoryId`/`vendorId` are unchanged (dates-only modification keeps its current behavior — no cutoff enforcement on a pure date change, see Boundaries — just gains the CAS write).
    Avoid: reading a vendor field off `quoteModification()`'s return value — it doesn't have one; write the request's own validated `targetVendorId` instead.

## DO NOT CHANGE

## SCOPE LIMITS
- No UI in this plan — the location/vehicle-type picker is 04-14, depends_on this plan.
- `pending`-status bookings do not count as availability conflicts (per user decision) — only `reserved`/`checked_in`.
- No `VehicleClass -[:EQUIVALENT_TO]-> VehicleClass` graph edge — cross-class equivalence matching is not in scope; `findEquivalentInventory()` takes an explicit `vehicleClassName`, it does not infer substitutes.
- `/api/payments/intent`'s pre-existing lack of server-side amount recompute stays an unfixed, disclosed gap (consistent with 04-08/04-12) — not addressed here.
- The modification-cutoff gate applies only to location/vehicle-type changes, per AC-3's own scope — a dates-only modification remains ungated by `modification_cutoff_hours` in this plan (an accepted, disclosed non-goal, not an oversight).
- `findEquivalentInventory()` has no HTTP-reachable caller in this plan — it is added for 04-14 to wrap in its own API route; 04-13 does not itself expose it over HTTP.
