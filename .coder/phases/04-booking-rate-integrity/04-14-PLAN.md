<objective>
## Goal
Add an alternate-vendor picker to the existing modify UI so a member can actually reach the cross-vendor swap built into 04-13's API, instead of that surface only being callable directly. **Scope note:** `findEquivalentInventory(locationLabel?, vehicleClassName?)` filters *to* a given location/class — it cannot itself surface a different location or vehicle class than the one passed in. This plan therefore scopes the picker to **alternate vendors/units at the booking's current location and vehicle class** (the case 04-13's cross-vendor re-quote logic actually targets). Browsing to a genuinely different location or vehicle class would require a new member-facing search step plus an HTTP-reachable wrapper around `findEquivalentInventory()` (which 04-13 explicitly does not provide) — that is out of scope here and, if wanted, is a follow-on plan, not part of 04-14.

## Purpose
04-13 made changing a reserved booking's inventory/vendor safe at the API layer (availability check, cutoff gate, correct cross-vendor re-quote, CAS write). Without a UI, none of that is reachable by a member — this plan closes that gap for the same-location/class, alternate-vendor case, per the user's "Full UI + API" scope decision for 04-13.

## Output
- `components/booking-modify-form.tsx`: gains an alternate-vendor picker step, sourced from `findEquivalentInventory()` called with the booking's own current location/class, wired into the existing debounced dry-run flow.
- `components/booking-modify-dialog.tsx`: passes through the new candidate list / selection state.
- Existing entry points (`My Bookings`, confirmation page) unchanged in shape — the confirmation page renders `BookingModifyForm` directly today (no dialog wrapper there); My Bookings keeps its existing dialog trigger. Both gain the richer form inside, no new page/route.

<boundaries>

## DO NOT CHANGE
- 04-13's API contract — this plan consumes it as-is; any endpoint gap found here should be flagged, not silently patched client-side.
- The existing dates-only modify UX when "Keep current vehicle" is selected — must remain byte-for-byte equivalent in behavior to pre-04-14.

## SCOPE LIMITS
- No new standalone page/route — the picker lives inside the existing `BookingModifyDialog`/`Form`.
- No client-side availability caching or "X units left" style claims — availability is only ever known via a dry-run response, per the platform/vendor boundary design.
- Picker is scoped to alternate vendors at the booking's *current* location and vehicle class only — browsing to a different location or vehicle class is not in scope for this plan (would require a new HTTP-reachable wrapper around `findEquivalentInventory()`, which 04-13 deliberately does not provide, plus a member-facing search/filter step this plan does not add).

</boundaries>
