<objective>
## Goal
Build the real, graph-backed Discovery/Search page: a server-rendered `/(discovery)/search` route that queries `lib/graph/queries.ts` for Inventory joined to VehicleClass, Vendor, NegotiatedTerm, and Perk, filtered by pickup location, and renders results using the BookCars-style sidebar + horizontal-card layout established in 04-03 — this time with real data instead of `mockVehicleClasses`.

## Purpose
This is the first real (non-prototype) screen in Discovery/Checkout. It replaces the mock search-results page as the actual product surface members will use, and its output (a selected Inventory/Vendor/NegotiatedTerm combination) is the direct input 04-05's checkout consumes. Getting the query layer right here — Inventory→VehicleClass→Vendor→NegotiatedTerm→Perk in one call — is the foundation the rest of Phase 4's booking/modification/cancellation flows build on.

## Output
- `lib/graph/queries.ts`: new `searchInventory(locationLabel?: string)` function returning one row per Inventory item with its VehicleClass, Vendor, matching NegotiatedTerm, and included Perks.
- `app/(discovery)/search/page.tsx`: real server component rendering that data in the 04-03 sidebar+card layout.
- `components/vehicle-card.tsx`: extracted horizontal result-card component (real-data version of 04-03's inline card JSX), used by the search page and reusable by 04-05's checkout summary.
</objective>

  <name>Task 1: Add searchInventory query joining Inventory/VehicleClass/Vendor/NegotiatedTerm/Perk</name>
  <files>lib/graph/queries.ts</files>
  <action>
    Add a new exported function `searchInventory(locationLabel?: string)`:
    - **NegotiatedTerm is keyed by (Vendor × MembershipTier), NOT by Inventory or VehicleClass** — `(MembershipTier)-[:ELIGIBLE_FOR]->(NegotiatedTerm)<-[:OFFERS_TERM]-(Vendor)`, per `ONTOLOGY.md`. This is an anonymous/unauthenticated search page with no member/tier context, so joining `(v:Vendor)-[:OFFERS_TERM]->(t:NegotiatedTerm)` directly (with no tier constraint) would fan out 3 rows per Inventory item (one per MembershipTier). Instead, resolve exactly one NegotiatedTerm per vendor: the term reachable via the **lowest-rank** MembershipTier (`MembershipTier.rank`, strict order Gold Star < Executive < Business — confirm the exact rank value/ordering by reading seeded `data/synthetic/membership_tiers.json` before hardcoding a rank number) — this is the publicly displayable "starting rate," analogous to a rate card shown before a member's actual tier is known.
    - Build a single Cypher query via `runCypher` that matches
      `(i:Inventory)-[:INSTANCE_OF]->(vc:VehicleClass)`,
      `(i)-[:OFFERED_BY]->(v:Vendor)`,
      `(i)-[:LOCATED_AT]->(l:Location)` (optional match — some seeded Inventory rows may lack it; do not fail the whole query if absent),
      `(mt:MembershipTier)-[:ELIGIBLE_FOR]->(t:NegotiatedTerm)<-[:OFFERS_TERM]-(v)` filtered to the lowest-rank `mt`,
      optional `(t)-[:INCLUDES_PERK]->(p:Perk)`.
    - When `locationLabel` is provided, filter with a WHERE clause on the Location node's label/city property (inspect the actual seeded property name in `data/reference/mock-data/rental_inventory.json`/graph init before hardcoding a property key — do not guess).
    - Return exactly one row per Inventory item: `{ inventory, vehicleClass, vendor, negotiatedTerm, perks: Perk[] }`, using `runCypher`'s existing `parseAgtype`/row-mapping pattern already used by `getVehicleClasses`/`getNegotiatedTermsForVendor`/`getPerksForTerm` in this file. Aggregate multiple `INCLUDES_PERK` rows for the same Inventory+NegotiatedTerm into a single `perks` array in JS (Cypher `collect()` inside AGE has known limitations here per this project's existing query style — do the aggregation step in TypeScript after fetching rows, same approach as the rest of this file already uses for simple per-node fetches). If a vendor has more than one NegotiatedTerm at the lowest rank tier (should not happen per the 30-row seed of 10 vendors × 3 tiers, but verify), take the first and log nothing — do not silently produce duplicate Inventory rows.
    - Add minimal TypeScript interfaces for the row shape (`InventorySearchResult` or similar) alongside the existing `VehicleClass`/`NegotiatedTerm`/`Perk` interfaces in this file — do not create a separate types file for this.
    - Avoid: introducing a second Postgres client/pool — reuse `runCypher` from `./client` exactly as the existing three functions do.
  </action>
