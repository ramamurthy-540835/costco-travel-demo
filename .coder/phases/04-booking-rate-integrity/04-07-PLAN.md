<objective>
## Goal
Let a member modify an existing reserved booking's dates (API also supports inventory/vendor changes, though the UI in this plan exposes dates only — see Output/Scope Limits) — through a real UI on the confirmation page AND from a new real "My Bookings" list page (not just an API, and not restricted to a single booking's own confirmation URL), with the negotiated rate re-derived live from the graph (not cached from the original booking) and any rate increase enforced via a real Stripe charge before the booking record changes. Introduce a dedicated `lib/vendor-integration/` module as the seam where vendor-contract-varying business rules live, so Phase 6's real Vendor Integration Layer can later replace its internals without touching route/UI code.

## Purpose
Closes UC2 (Modification routed to vendor with rate re-application). Two things converge in this revision of the plan, per explicit user direction:
1. **UI, not API-only.** The original draft was API-only; the confirmation page (`app/(checkout)/confirmation/[bookingId]/page.tsx`) already exists as the real per-booking view built in 04-05/04-12, so this plan adds a "Modify your booking" card there, reusing 04-12's established checkout UI patterns (shadcn `Card`/`Button`, lucide icons, a client component with live total recalculation and a Stripe Elements step for any delta charge — see `app/(checkout)/checkout/checkout-form.tsx`).
2. **A real platform/vendor boundary, not logic scattered in route handlers.** PROJECT.md already establishes the target architecture — Discovery/Checkout (this platform) vs. Fulfillment (an independently-deployed Vendor Integration Layer, no shared code, joined only via graph + RPC) — but that boundary doesn't exist yet inside this codebase; every route that touches vendor-contract data (rates, policies) calls graph queries directly and inline. This plan is the first to introduce `lib/vendor-integration/`: a module that encapsulates "what does this vendor currently offer for this modification" behind a stable function signature. Today it's an in-process call against the shared graph; when Phase 6 stands up the real Vendor Integration Layer service, only this module's internals change to an RPC call — routes and UI never do. 04-08 will add a second function to the same module for cancellation policy, establishing the pattern rather than each plan inventing its own ad hoc boundary.
3. **Not restricted to the single-booking confirmation URL.** A member currently has no way to find a past booking's confirmation page again except a bookmarked link — the only real per-account view is the mock `/prototype/bookings`. This plan adds a real "My Bookings" list page (`app/(account)/bookings/page.tsx`) with status/date filters, and the same `BookingModifyForm` this plan builds is reachable from there (via a dialog per row), not only from the one booking's own confirmation page. 04-08 adds the equivalent cancel affordance to the same list page, symmetrically (see that plan's Task 6).

## Output

<acceptance_criteria>

## AC-1: Date-only modification with no rate change re-prices correctly
```gherkin
Given a member owns a `reserved` Booking for inventory X from day 1-3 (2 nights)
When they submit a modification changing dates to day 1-5 (4 nights), same inventory
Then the Booking's `from`/`to` update, `pricingSnapshot.totalPrice` is recomputed as dailyRate*4 + addonTotal (using the current graph rate for that inventory, not the stale stored rate), and the prior snapshot + dates are appended to `modificationHistory`
```

## AC-2: Price-increasing modification requires a matching successful payment
```gherkin
Given a modification's recomputed total is higher than the current pricingSnapshot.totalPrice
When the member submits the modification without a paymentIntentId, or with one whose Stripe amount does not match the price delta (in cents, within a ±1 cent tolerance for dollar-rounding)
Then the API returns 400 and the Booking is not modified
```

## AC-3: Price-increasing modification succeeds with a valid delta payment, end to end through the UI
```gherkin
Given a member is viewing their confirmation page for a `reserved` booking, and picks new dates that raise the total by $X in the "Modify your booking" card
When they confirm the delta payment through the Stripe Elements step shown in that card
Then the card shows the updated total, the page reflects the new dates/pricingSnapshot on reload, and the underlying API call enforces the same server-side rate re-derivation and payment check as AC-1/AC-2 (the UI is not a trusted shortcut around them)
```

## AC-4: Only the owning member can modify their booking
```gherkin
Given Booking B belongs to member A
When member B (a different signed-in Clerk user) calls POST /api/bookings/{B's id}/modify directly (bypassing the UI)
Then the API returns 404 (not found — no ownership leaked) and the Booking is unchanged
```

## AC-5: The vendor-integration boundary is the only place rate-requote logic lives
```gherkin
Given the modify route needs the vendor's current rate/perks for a given inventoryId/vendorId/date range
When it needs that data
Then it calls `quoteModification()` from `lib/vendor-integration/policy.ts` — it does not call `searchInventory()` directly itself
```

## AC-6: My Bookings lists the member's own bookings, filterable, with Modify reachable from there
```gherkin
Given a signed-in member with 3+ bookings in different statuses (e.g. reserved, cancelled)
When they visit `/bookings` (linked from the header) and apply a status filter
Then only bookings matching that status render, each showing vendor/dates/total, and any `reserved` row's "Manage" action opens the same `BookingModifyForm` used on that booking's own confirmation page (not a duplicate, divergent implementation) — reachable without knowing that booking's confirmation URL
```

  <name>Task 2: Modification API route, built on the vendor-integration module</name>
  <files>app/api/bookings/[id]/modify/route.ts</files>
  <action>
    Create `POST /api/bookings/[id]/modify`:
    1. `auth()` — 401 if not signed in.
    2. Fetch `Booking.findById(params.id)`; 404 if null. Look up `Member.findOne({ clerkUserId: userId })`; if no Member, or `String(booking.member) !== String(member._id)`, return 404 (AC-4's ownership-hiding pattern — a missing booking and a not-your-booking both return the same 404 shape).
    3. If `booking.status !== 'reserved'`, return 400 `{ error: 'Only reserved bookings can be modified' }`.
    4. Accept body `{ inventoryId?: string, vendorId?: string, from?: string, to?: string, paymentIntentId?: string, dryRun?: boolean }`. Default `inventoryId`/`vendorId`/`from`/`to` to the booking's current values if omitted.
    5. Call `quoteModification({ vendorId, inventoryId, from, to })` from `lib/vendor-integration/policy.ts` — do not call `searchInventory()` in this route file (AC-5). 400 `{ error: 'Inventory or negotiated rate not found' }` if it returns `null`.
    6. Recompute `nights` from the new `from`/`to`. Re-filter the booking's existing `pricingSnapshot.addonIds` against `quote.perkIds`' waived set — call `getWaivedAddOnIds(quote.perkIds)` (same function `app/api/bookings/route.ts` uses at creation) and drop any previously-selected addon id that the *new* quote's perks now waive, exactly mirroring the creation-time logic. This matters because `inventoryId`/`vendorId` are modifiable, so the perk set backing the addon selection can change — carrying the addon list over unfiltered would risk re-charging for an addon the new vendor/perk combination already includes free (this is the project's UC6 "no already-included perk re-charged" guarantee, and it must hold across a modification too, not just at creation). Recompute `addonTotal` for the (re-filtered) addon ids at the current `fee_per_day` × new `nights`, via `getAddOnsCatalog()` (direct graph-query call, not part of the vendor-policy boundary — the addon catalog is platform-side pricing data, not a vendor-contract rule; `getWaivedAddOnIds` is the same kind of direct, non-boundary call).
    7. `newTotalPrice = quote.dailyRate * nights + addonTotal`. `deltaCents = Math.round(newTotalPrice * 100) - Math.round(booking.pricingSnapshot.totalPrice * 100)` (round each side to cents before subtracting, not after — avoids float drift false-rejecting a correct delta payment).
    8. **`dryRun: true` is a pure, universal no-op** — checked first, before any other branching: if `dryRun === true`, always return `{ deltaCents, newTotalPrice }` with 200 and return immediately, without touching the Booking, regardless of whether `deltaCents` is positive, zero, or negative. (Task 3's UI calls this on every date change to show a live preview — if a previewed date happens to be cheaper, a non-strict dry-run would silently apply that "preview" as a real modification, which is the bug this ordering prevents.)
    If `dryRun` is not `true` and `deltaCents > 0`: require `paymentIntentId`; retrieve it via `getStripe().paymentIntents.retrieve(...)`; require `status === 'succeeded'`. Compare `paymentIntent.amount` to `deltaCents` with a **±1 cent tolerance**, not strict equality (`/api/payments/intent` receives `amount: deltaCents / 100` in dollars and does `Math.floor(amount * 100)`, which can round-trip a cent off due to floating point — e.g. `29` cents → `$0.29` → `28`; strict equality would spuriously reject a genuinely-correct payment for such values). On a mismatch outside that tolerance, 400 `{ error: 'Payment does not cover the price increase' }`, Booking untouched, and **do not** attempt any refund of that PaymentIntent here — a captured-but-rejected delta payment is a known, out-of-scope reconciliation gap for this plan (see Boundaries); the response should say so (`{ error: 'Payment does not cover the price increase', note: 'If you were charged, contact support — this modification was not applied' }`) rather than implying the charge was reversed.
    If `dryRun` is not `true` and `deltaCents <= 0`: proceed directly to apply (step 9) — no PaymentIntent required.
    9. On a real (non-dry-run) apply: push `{ from: booking.from, to: booking.to, inventoryId: booking.inventoryId, vendorId: booking.vendorId, pricingSnapshot: booking.pricingSnapshot }` onto `modificationHistory`, set `booking.inventoryId/vendorId/from/to` and the new `pricingSnapshot` (`negotiatedTermId: quote.negotiatedTermId, dailyRate: quote.dailyRate, currency: quote.currency, perkIds: quote.perkIds, addonIds: <the re-filtered list from step 6>`, `addonTotal, totalPrice: newTotalPrice`). Save. Return `{ bookingId: String(booking._id), totalPrice: newTotalPrice, deltaCents }` with 200.
    Avoid: recomputing rate from the booking's stored `pricingSnapshot` — always re-derive via `quoteModification()`.
  </action>
