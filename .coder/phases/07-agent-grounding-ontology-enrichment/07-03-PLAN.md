<objective>
## Goal
Expose the graph to Phase 8/9 agents via 3 composable, generic retriever tools — `lookupNode`, `traverse`, `resolveSynonym` — instead of one opaque search call, per ROADMAP.md's Phase 7 scope note ("2-3 composable retriever tools ... per the GraphRAG multi-tool pattern — this is the tool surface Phase 8/9's agents will call").

## Purpose
`lib/graph/queries.ts` currently only has bespoke, hardcoded functions (`getVehicleClasses`, `getPerksForTerm`, `getEquivalenceCandidates`, ...) — each one is a fixed Cypher shape for one caller's exact need. Neither the Phase 8 Vendor Agent nor the Phase 9 Customer/Driver Assistant exists yet, and neither should have to grow its own new bespoke query function every time it needs a slightly different lookup. A small, generic, composable tool surface — parameterized by label/property rather than hardcoded per entity type — lets both future agents (and any LLM tool-calling layer wrapping them) do real graph retrieval without this project's data layer growing one-off functions per prompt. This directly closes Phase 7's last scope item; once this plan lands, Phase 7 (3/3 plans) is complete and the roadmap transitions to Phase 8.

## Output
- New `lib/graph/retrievers.ts`:
  - `lookupNode(label: string, matchProperty: string, matchValue: string): Promise<Record<string, unknown> | null>` — single-node-by-property lookup, generic across all 14 `NODE_LABELS`
  - `traverse(fromLabel, fromProperty, fromValue, edgeType, toLabel, direction): Promise<Record<string, unknown>[]>` — one-hop traversal in either direction, generic across the schema's real edge types (`OFFERS_TERM`, `INCLUDES_PERK`, `PART_OF_CLUSTER`, `RESERVED`, etc.)
  - `resolveSynonym(term: string): Promise<{ label: string; matchProperty: string; canonical: Record<string, unknown> }[]>` — case-insensitive search across every node label carrying a `synonyms` array property (`VehicleClass`, `Perk`, `AddOn`, `MembershipTier`, `Location`, `Intent`), returning the canonical node(s) whose `synonyms` list contains the term
- `lib/graph/queries.ts` unchanged in its existing exports (boundary — see below) but reviewed for whether any 2+ existing bespoke functions are now trivially expressible as a `traverse()` call, documented in SUMMARY.md as a deferred refactor (not performed this plan, to avoid touching Phase 4-6 route call-sites)
- `agent-lab/`'s demo extended with a small "Retriever Tools" section demonstrating each of the 3 tools against the live graph (real output, not mocked), so Phase 8/9 authors have a runnable reference before writing agent code
- `ONTOLOGY.md`/`VOCABULARY.md` updated to document the retriever-tool surface as the sanctioned way future agents query the graph
</objective>

    `lookupNode(label, matchProperty, matchValue)`: build the Cypher string with the label interpolated (label/property names are never user-supplied free text at the call site — they're fixed string literals chosen by the calling agent-tool code, same trust boundary as every existing `queries.ts` function's hardcoded label; only `matchValue` is a runtime value, and it MUST go through the `$`-parameterized `runCypher` params object, never string-interpolated, to avoid Cypher injection). Cypher: `` MATCH (n:${label} {${matchProperty}: $matchValue}) RETURN n LIMIT 1 ``, params `{ matchValue }`, columns default (single `result`). Return `rows.length > 0 ? rows[0].properties : null`.

    `traverse(fromLabel, fromProperty, fromValue, edgeType, toLabel, direction)`: `direction` is `"out" | "in"`. Build Cypher as `` MATCH (from:${fromLabel} {${fromProperty}: $fromValue})-[:${edgeType}]->(to:${toLabel}) RETURN DISTINCT to `` for `"out"`, or with the arrow reversed (`<-[:${edgeType}]-`) for `"in"`. Params `{ fromValue }`. Return `rows.map(r => r.properties)`.

    `resolveSynonym(term)`: cross-label search over exactly these 6 labels — `VehicleClass`, `Perk`, `AddOn`, `MembershipTier`, `Location`, `Intent`. Note `graph/graph_service/schema.py` only defines `NODE_LABELS`/`EDGE_ENDPOINTS` (label/edge names, no property-level schema) and CANNOT itself confirm which labels carry `synonyms` — the real evidence is `graph/scripts/load_seed_data.py`'s hand-seeded `*_SYNONYMS` dicts (VehicleClass/Perk/AddOn/MembershipTier), 07-02's `backfill_synonyms.py`/`verify_graph.py` (Location, LLM-generated), and `verify_graph.py`'s own `Intent` non-empty-synonyms check plus `agent-lab/scripts/generate_knowledge_graph_demo.py`'s `MATCH (i:Intent) RETURN i.intent_id, i.synonyms` query (Intent, seeded via `data/synthetic/agent_intents.json` per Phase 2's 02-01) — confirm the full 6-label set against these real sources live (e.g. a quick cypher spot-check per label) before finalizing, in case a label was added or dropped since this plan was written. - Any existing exported function in `lib/graph/queries.ts` — this plan adds a parallel generic surface, it does not refactor or replace the bespoke functions Phase 4-6 routes already call
- `lib/graph/client.ts` — `runCypher`'s existing contract is sufficient; no changes needed

## SCOPE LIMITS
- No LLM/agent runtime code, no tool-calling framework wiring (e.g. no OpenAI/Anthropic tool-schema definitions) — that's Phase 8/9's concern per ROADMAP.md's Phase 7 "Not in scope" note; this plan only builds the underlying TypeScript functions those future tool schemas will wrap
- No multi-hop traversal (2+ edges in one call) — `traverse()` is one-hop only; composing multiple one-hop calls is the caller's job, keeping this tool's Cypher simple and label-agnostic
- No caching/memoization layer — out of scope, a future performance concern if/when Phase 8/9 agents show it's needed
- No refactor of existing bespoke `queries.ts` functions to use the new retrievers internally — noted as a deferred possibility in SUMMARY.md only, not performed
