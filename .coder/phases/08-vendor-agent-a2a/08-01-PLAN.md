<objective>
## Goal
Stand up the Vendor Agent as a separate deployable process exposing a static Agent Card and a JSON-RPC `/a2a` endpoint over the 4 skills (`check_availability`, `apply_modification`, `apply_cancellation`, `get_vendor_policy`), all wrapping the existing `lib/vendor-integration/policy.ts` boundary module rather than reimplementing its logic.

## Purpose
Closes Phase 8's own boundary requirement (PROJECT.md: "vendor integration is a separate service/RPC boundary, no shared code with Discovery/Checkout") and gives Phase 9's Customer/Driver Assistant a real A2A surface to call instead of importing `policy.ts` directly. Minimal A2A conformance now (`submitted|completed|failed` only, per the 2026-09-07 decision recorded in ROADMAP.md), but built extensibly so Phase 9 can add `input-required`/`auth-required` without a rewrite.

## Output
- `agent-service/vendor-agent/` — a standalone Node process (own port, run via `tsx`, no Next.js/Express dependency), separate from the Next.js app process but living in the same repo/image (parameterized-per-vendor topology — one process serves all 10 seeded vendors)
- Static Agent Card at `GET /.well-known/agent-card.json`
- JSON-RPC 2.0 `POST /a2a` implementing `message/send`, dispatching to the 4 skills
- `agent-service/vendor-agent/README.md` with real curl examples for the Agent Card and each skill, live-verified
- ONTOLOGY.md/VOCABULARY.md updated with the new A2A skill surface
</objective>


  <files>agent-service/vendor-agent/server.ts, agent-service/vendor-agent/agent-card.ts, package.json</files>
  <action>
    Use Node's built-in `http` module only (no new dependency — this repo has no Express/Fastify; adding one for a single small endpoint isn't warranted).

    `agent-service/vendor-agent/agent-card.ts`: export a `const AGENT_CARD` object matching the A2A Agent Card shape (name: "Vendor Agent", description, url pointing at this process's own `/a2a`, and a `skills` array of exactly 4 entries — `check_availability`, `apply_modification`, `apply_cancellation`, `get_vendor_policy` — each with `id`, `name`, `description`, and a plain-object `inputSchema` naming its required params, e.g. check_availability needs `vendorId, inventoryId, from, to`).

    `agent-service/vendor-agent/server.ts`:
    - Define `type TaskState = 'submitted' | 'working' | 'completed' | 'failed' | 'input-required' | 'auth-required'` and a `Task` interface `{ id: string, status: { state: TaskState, message?: string }, result?: unknown }`. Only `submitted`/`completed`/`failed` are ever assigned in this plan's dispatch code — the other two members exist only as forward-compatible union members for Phase 9, and a one-line comment must say so (not a TODO to implement now).
    - `http.createServer` handling: `GET /.well-known/agent-card.json` → 200 + `AGENT_CARD` JSON. `POST /a2a` → read/parse the JSON-RPC 2.0 body (`{jsonrpc: '2.0', method: 'message/send', params: {skill, vendorId, ...args}, id}`), reject non-`message/send` methods with a JSON-RPC error response (code -32601), dispatch `params.skill` to the skill registry built in Task 2, and return the resulting `Task` wrapped in a JSON-RPC result envelope. Any other path → 404.
    - Read the listen port from `process.env.VENDOR_AGENT_PORT`, default `4100`. Log the port and Agent Card URL on start.
    - Avoid: pulling in Next.js request/response types — this process is not part of the Next.js app and must run standalone via `tsx agent-service/vendor-agent/server.ts`.

    Add an npm script `"vendor-agent:dev": "tsx agent-service/vendor-agent/server.ts"` to `package.json`.

    Env loading: unlike `next dev`/`next build`, a plain `tsx` invocation does NOT auto-load `.env.local` — and this repo has no `dotenv` dependency. `MONGODB_URI` and `GRAPH_DATABASE_URL` (both required by `lib/mongodb.ts` / `lib/graph/client.ts`, both defined only in `.env.local`) would be `undefined`, and the first Mongo/graph call would throw "Please define the ... environment variable". At the very top of `server.ts`, before any other import that could trigger a Mongo/graph call, add a small dependency-free loader: if `.env.local` exists in the repo root, read it, split into lines, skip blank/`#`-comment lines, split each remaining line on the first `=`, and `process.env[key] = process.env[key] ?? value` (never override a var already set in the shell). Do this with `fs`/`path` only — no new dependency.
  </action>
  <verify>npx tsc --noEmit; then `npm run vendor-agent:dev &` and `curl -s localhost:4100/.well-known/agent-card.json | python3 -m json.tool` shows exactly 4 skills</verify>

  <name>Task 2: Wire the 4 skills to lib/vendor-integration/policy.ts</name>
  <files>agent-service/vendor-agent/skills.ts, agent-service/vendor-agent/server.ts</files>
  <action>
    Create `agent-service/vendor-agent/skills.ts` exporting a `SKILLS: Record<string, (args: any) => Promise<Task>>` registry (import the `Task`/`TaskState` types from `server.ts`, or hoist them to a shared `agent-service/vendor-agent/types.ts` if that avoids a circular import — pick whichever compiles cleanly). Import `lib/vendor-integration/policy.ts`, `lib/graph/queries.ts`, and `lib/mongodb.ts` using relative paths (e.g. `../../lib/vendor-integration/policy`), not the `@/lib/...` alias used inside the Next.js app — `agent-service/vendor-agent/` is outside Next's own module graph and this avoids depending on `tsx`'s tsconfig-paths resolution behaving identically to Next's bundler resolution.

    Each handler calls `lib/mongodb.ts`'s `connectToDatabase()` first if it touches Mongo (mirrors every existing API route's pattern — `policy.ts` itself never connects), then:
    - `check_availability(args: {vendorId, inventoryId, from, to})`: call `checkAvailability({ inventoryId, from: new Date(from), to: new Date(to) })` from `policy.ts`. Return a `completed` Task with `result: { available: boolean }`.
    - `apply_modification(args: {vendorId, inventoryId, from, to})`: call `quoteModification({vendorId, inventoryId, from, to})` and `checkModificationCutoff(vendorId, new Date(from))`. If the quote is `null` (unknown vendor/inventory pair) or the cutoff check disallows it, return a `failed` Task with a specific `status.message` (name which check failed). Otherwise return `completed` with `result: { quote, cutoff }`.
    - `apply_cancellation(args: {vendorId, hoursUntilStart})`: call `quoteCancellation({vendorId, hoursUntilStart: Number(hoursUntilStart)})`. `null` → `failed` Task (unknown vendor). Otherwise `completed` with `result: quote`.
    - `get_vendor_policy(args: {vendorId})`: call `getVendorPolicy(vendorId)` from `lib/graph/queries.ts`. `null`/undefined → `failed`. Otherwise `completed` with `result: policy`.

    Every handler wraps its logic in try/catch — a thrown error (bad graph connection, malformed date) becomes a `failed` Task with the error's message, never an uncaught exception that would 500 the HTTP response. Wire `server.ts`'s `/a2a` dispatch to look up `SKILLS[params.skill]`; an unknown skill name returns a `failed` Task, not a JSON-RPC method-not-found (the RPC method is always `message/send` — the skill name is an application-level param, not the RPC method).

    Avoid: duplicating `checkAvailability`/`quoteModification`/etc.'s logic here — every handler is a thin call-through plus Task-shape translation.
