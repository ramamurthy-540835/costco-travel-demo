# Research: Platform/Vendor Agentic Boundary — Implications for 04-13

## Reference Pattern: mastech-agentic-commerce's Store Ops Agent / A2A boundary

The Store Ops Agent is a **genuinely separate process** (`agent-service/agent_service/store_ops/service.py`), not an in-process module — it runs its own Starlette app on its own port (`STORE_OPS_SERVICE_URL`, default `:8100`) and is reached only over HTTP. It publishes a static capability description at `/.well-known/agent-card.json` (`agent_card.py`): protocol version, a human-readable description deliberately scoped ("checking real stock ... without revealing exact stock counts"), a `skills` list derived from its own tool definitions (`check_inventory`, `find_equivalence_candidates`, `get_local_offer`), and an `agentInterfaces` entry pointing at a JSON-RPC 2.0 endpoint (`/a2a`). This "agent card" is the machine-readable capability contract — the storefront never needs to know *how* the store answers, only that it exposes these named skills at this URL.

The RPC contract itself (`store_ops_client_tool.py` on the client side, `a2a_route` in `service.py` on the server side) is a synchronous JSON-RPC 2.0 `message/send` call: a `data` Part carrying `{request_type, sanity_id, store_id}` in, a Task object back with `status.state` (`completed`/`failed` only — no intermediate "working" state, since it's one HTTP round trip) and an `artifacts[].parts[].data` payload (`substitution_response`: stock status + candidate substitutes + local offer, explicitly never `qty_on_hand`). Every failure mode (connection refused, timeout, malformed body, JSON-RPC error, Task-level failure) collapses to the same `{"original_sku_status": "unknown", ..., "error": "store_ops_agent_unreachable"}` shape on the client side — the storefront never distinguishes "store is down" from "store said no," and the tool call never raises.

Authority split is enforced structurally, not just by convention: `check_inventory`/`find_equivalence_candidates`/`get_local_offer` (`agent-service/agent_service/store_ops/tools.py`) read `inventory_facts`/`local_offers` — vendor-owned, live, per-store tables — directly, gated by `check_access(actor, "read", ...)` and `record_audit(...)`, and only the Store Ops Agent process holds that DB access; a single hardcoded `STORE_OPS_ACTOR_ID` acts on its own behalf (no caller-supplied actor identity is ever trusted). The storefront's shared `commerce_graph` (Postgres+AGE) holds only what both sides are allowed to see without a live check — Product, EquivalenceCluster, category/attribute vocabulary — genuinely non-sensitive, non-live catalog structure. **Live per-store stock counts and local promotional pricing never enter the shared graph** — they live in vendor-side SQL tables reachable only through the RPC boundary, and the boundary function explicitly refuses to reveal the underlying quantity even when it has it (returns status enum only, per spec §5's franchise-side constraint). That is the core precedent: shared graph = structural/catalog truth; RPC boundary = live, sensitive, vendor-authoritative operational state.

## Current State in mastech-agentic-travel

`lib/vendor-integration/policy.ts` is explicitly written as this project's "Phase 6 seam" — its own header comment states the intent precisely: "Today it answers that question in-process against the shared knowledge graph... When Phase 6 stands up the real, independently-deployed Vendor Integration Layer service, only this file's internals change to an RPC call — callers in `app/api/bookings/[id]/*/route.ts` never need to change." `quoteModification({vendorId, inventoryId, from, to})` and `quoteCancellation({vendorId, hoursUntilStart})` are the two boundary functions today, and both already carry forward-compatibility markers: `quoteModification`'s `from`/`to` params are accepted but unused ("today's graph-only implementation has no per-date availability data... these params aren't yet used beyond being present in the contract" — the comment names exactly the gap 04-13 needs to fill).

`lib/graph/queries.ts`'s `searchInventory()` currently reads `Inventory`/`VehicleClass`/`Vendor`/`Location` nodes plus each vendor's lowest-rank `NegotiatedTerm`/`Perk` — i.e., static catalog shape (what vehicle classes/models a vendor lists, at what city) plus platform-owned negotiated-rate data. `getVendorPolicy()` reads `VendorPolicy` (cancellation window, no-show fee) — also platform/vendor-contract data, not live operational state. Per `ONTOLOGY.md`, `Inventory` presently has no per-date/per-unit availability property at all — it's a catalog row (make/model/class/daily_rate/deposit), not a live fleet-state record. This is why `policy.ts`'s own header calls this a "mock-data-era shortcut" implicitly: the graph is *already* being used as if it were catalog data, which today is harmless because there is no real vendor system behind it and no availability data exists yet to leak. The moment 04-13 needs a real availability answer ("is `inventoryId` X free for these new dates"), the naive move — adding an `availableFrom`/`availableTo` or `bookedRanges` property to `Inventory` and querying it via Cypher from `app/api/bookings/[id]/*/route.ts` — would put live, vendor-authoritative fulfillment state into the shared platform graph, exactly the boundary Store Ops Agent's `inventory_facts` table was kept out of `commerce_graph` to avoid.

`lib/models/Booking.ts` already models the vendor/inventory relationship correctly for a broker: `inventoryId`/`vendorId` are plain strings referencing graph node ids, not a Mongoose `ref` — this platform never owns an `Inventory` document, matching the "no shared code/imports" spirit. `pricingSnapshot` and `modificationHistory[].pricingSnapshot` freeze negotiated-term/perk/rate data at transaction time, which is the platform's own authoritative record and correctly lives in Mongo, not the graph. `modificationHistory` already has the shape 04-13 needs to append to (`from`, `to`, `inventoryId`, `vendorId`, `pricingSnapshot`, `modifiedAt`) — a location/vehicle-type-change modification is structurally just another entry here, with the same `vendorId`/`inventoryId` swapped for a cross-vendor re-match.

## Gap Analysis for 04-13

04-13 needs two things `policy.ts` doesn't yet do: (1) an availability check for a *target* `inventoryId`/date range (possibly a different inventory than the one currently booked, if the location/vehicle-type change forces a re-match), and (2) for cross-vendor re-match, a search across vendors' catalogs for an equivalent-class alternative when the original vendor has no matching inventory at the new location.

- **Availability check, built naively**: adding a "is this reserved" flag/date-range property onto the `Inventory` graph node and having a Next.js route Cypher-query it directly reaches directly into what should be vendor-fulfillment-owned state (which specific unit is free when) — exactly the `inventory_facts` table in the reference pattern, which deliberately lives outside `commerce_graph`. Doing this today is low-risk only because there is no real vendor system yet and no other consumer depends on that graph property being anything but a platform stand-in — but it plants a property that Phase 6's real Vendor Integration Layer would need to either take over or contradict, and every existing caller that queried it directly (`searchInventory()`, any future admin/dispute UI) would need to be found and re-pointed at the RPC call. The safer path (mirroring `policy.ts`'s own documented intent) is to answer the availability question through a **new function in `lib/vendor-integration/policy.ts`** — e.g. `checkAvailability({vendorId, inventoryId, from, to})` — even though today its "real" implementation is just a Mongo query against existing `Booking` documents for overlapping date ranges on that `inventoryId` (the platform's *own* bookings, which is legitimately platform data, not vendor fleet state) or a static graph read. This keeps the call-site shape RPC-ready without touching the graph schema.
- **Cross-vendor re-match, built naively**: this is closer to what's already legitimate — matching against `VehicleClass`/`Location`/`NegotiatedTerm` to find "another vendor offering an equivalent class at the new city, at a rate this member is eligible for" is exactly catalog + negotiated-rate structure, the same shape `searchInventory()` already reads. This part is fine as a graph read *as long as* the result is treated as a **candidate list**, not a confirmed reservation — confirming that a specific candidate `inventoryId` is actually available/booked-not-double-booked must go back through the same `checkAvailability()` boundary call before the modification is finalized, otherwise the graph search silently becomes the source of truth for live fulfillment state through the back door.

## Proposed Ontology/Knowledge-Graph Changes

| Node/Edge | Add or do-NOT-add | Rationale |
|---|---|---|
| `Inventory.bookedRanges` / `Inventory.availableFrom/To` property | **Do NOT add** | Live per-unit availability is vendor-fulfillment state (mirrors `inventory_facts` staying out of `commerce_graph`). Belongs behind the RPC boundary (`policy.ts`), backed today by Mongo `Booking` overlap query, by a real Vendor Integration Layer answer in Phase 6. |
| `Inventory`-[:AVAILABLE_AT]->`Location` (candidate re-match target) | **Add, if needed** | Static catalog fact ("this vendor lists this vehicle class at this city") — same shape as existing `LOCATED_AT`/`OFFERED_BY`. Used only to produce re-match *candidates*, never to confirm booking-level availability. |
| `VehicleClass` equivalence/compatibility edge (e.g. `(VehicleClass)-[:EQUIVALENT_TO]->(VehicleClass)`) | **Add, if 04-13 needs cross-class fallback** | Structural/taxonomic fact (mirrors agentic-commerce's `EquivalenceCluster`/`PART_OF_CLUSTER`) — legitimately shared-graph data, not vendor-live state. Only needed if 04-13's re-match must cross vehicle classes, not just vendors within the same class. |
| Any "reservation hold/lock" node representing an in-progress modification claim on a target unit | **Do NOT add to graph** | This is transactional/operational state, which the reference pattern keeps entirely inside Mongo/Postgres app tables (never the shared ontology graph) — mirrors `Booking`/`modificationHistory` already living in Mongo, not the graph. |

## Proposed Downstream Dependency Changes

| File / Function | Change | Rationale |
|---|---|---|
| `lib/vendor-integration/policy.ts` | Add `checkAvailability({vendorId, inventoryId, from, to}): Promise<{available: boolean}>` implemented today via a Mongo `Booking.find()` overlap query (own bookings) — NOT a graph read | Gives 04-13 the availability answer through the documented Phase-6 seam, same pattern as `quoteModification`/`quoteCancellation`; callers never change when Phase 6 swaps this to a real RPC call. |
| `lib/graph/queries.ts` | Add a `findEquivalentInventory({vehicleClass, city, excludeVendorId})`-style function limited to catalog+negotiated-term joins (mirrors `searchInventory()`) | Produces cross-vendor re-match *candidates* only — explicitly documented as candidates, not confirmed availability, so callers know a `checkAvailability()` call is still required before finalizing. |
| `app/api/bookings/[id]/*/route.ts` (new modify-location/vehicle-type route, 04-13) | Sequence: graph read for candidates → `policy.ts` `checkAvailability()` per candidate → `policy.ts` `quoteModification()` for the winning candidate → optimistic-lock `findOneAndUpdate` write to `Booking` (same pattern as 04-07/04-08) | Keeps graph reads (catalog/rate truth) and boundary calls (live/authoritative fulfillment truth) as two distinct steps instead of one Cypher query that conflates them. |
| `lib/models/Booking.ts` | No schema change required — `modificationHistory[]` entries already carry `inventoryId`/`vendorId`/`pricingSnapshot`; a location/vehicle-type change is just another entry with new `inventoryId`/`vendorId` | Confirms 04-13 can reuse the existing modification audit shape without inventing new fields. |
| `.coder/PROJECT.md` (Technical Context) | When 04-13 lands, note explicitly that `checkAvailability()` was added to `policy.ts` as the seam for future live-availability RPC, and that `Inventory` deliberately still has no live-availability property | Keeps the boundary rationale documented for whoever builds Phase 6, so the "why is this in Mongo not the graph" decision isn't re-litigated. |

## Open Questions for Planning

1. Does 04-13 need cross-vehicle-class fallback (triggering the `EQUIVALENT_TO` edge), or is a same-class-different-vendor/city re-match sufficient for this phase? Affects whether that ontology edge is added now or deferred.
2. Should `checkAvailability()` also account for *other* pending/in-flight modifications on the same target `inventoryId` (a race between two members' modification requests), or is Mongo's existing optimistic-lock `findOneAndUpdate` pattern on the `Booking` document sufficient to prevent double-booking at write time? The reference pattern's synchronous single-round-trip A2A call suggests the future real Vendor Integration Layer would itself serialize concurrent holds — worth flagging as a Phase 6 concern, not a 04-13 one.
3. Should the new `findEquivalentInventory()` candidate list be capped/ranked by negotiated-rate value (cheapest first) or by vendor rating, and does that ranking logic belong in `lib/graph/queries.ts` or in the route handler?
